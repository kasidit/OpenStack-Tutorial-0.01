OpenStack

บทที่ ๑ การใช้งานโอเพนสแตค

การใช้งานระบบโอเพนสแตคผ่าน Web Dashboard และ Command Line Interfaces

การใช้งานระบบโอเพนสแตคสามารถทำได้ 3 วิธีได้แก่

  1. Web Interface หรือ OpenStack Dashboard ออกแบบมาให้สะดวกต่อการใช้งานและทำให้ผู้ใช้มองเห็นภาพรวมของระบบประมวลผลแบบโครงสร้างพื้นฐานที่ผู้ใช้สร้างขึ้นได้ง่าย (Jackson 2018) (บรรยายในบทที่ ๑.2)

  2. Command Line Interfaces (CLI) เพื่อสร้างสคริปต์สำหรับออกคำสั่งเป็นปริมาณมาก (Jackson 2018) (บรรยายในบทที่ ๑.3)

  3. Application Programming Interfaces อนุญาตให้ผู้ใช้สั่งงานโอเพนสแตคจากแอปพลิเคชัน (นอกขอบเขตของหนังสือเล่มนี้ ผู้อ่านสามารถดูเพิ่มเติมได้ที่ https://developer.openstack.org)

๑.1 ขอบเขตการเข้าถึงและใช้งานทรัพยากร

ขอบเขตการใช้งานทรัพยากรของโอเพนสแตคมีสามระดับดังภาพ ๑-1 ได้แก่ ระดับ System (หรือ system-wide) ระดับ Domain และระดับ Project ระดับ System หมายถึงทรัพยากรทั้งหมด ระดับ Domain คือทรัพยากรส่วนหนึ่งที่ถูกจัดสรรให้กับผู้ใช้ขนาดใหญ่ เช่น องค์กร หรือบริษัท เป็นต้น ระดับ Project คือการแบ่งทรัพยากรภายใน Domain หนึ่งย่อยลงไปอีกให้กับผู้ใช้กลุ่มย่อยภายใน Domain เช่น แผนกของบริษัท หรือโครงการภายในองค์กร เป็นต้น

ใน System ผู้ดูแลระบบสามารถสร้าง Domain หลาย Domain โดยที่แต่ละ Domain มี Namespace แยกจากกัน ทำให้ผู้ใช้ใน Domain หนึ่งสามารถกำหนดชื่อ Project ชื่อบัญชีผู้ใช้ หรือชื่ออื่นๆ ซ้ำกับของ Domain ได้ ด้วยเหตุนี้ โอเพนสแตคจึงสามารถรองรับการประมวลผลขององค์กรหลายองค์กรได้โดยไม่ต้องกังวลว่าชื่อจะซ้ำกัน ตามปกติแล้ว โอเพนสแตคจะสร้าง default domain ขึ้นเป็น Domain เริ่มต้น ผู้ดูแลระบบสามารถสร้าง Domain เพิ่มเติมได้ภายหลัง เช่นเดียวกัน ผู้ใช้ในระดับ Domain สามารถสร้าง Project ได้หลาย Project ซึ่งแต่ละอันมี Namespace แยกจากกันโดยไม่ต้องกังวลว่าชื่อของ Instances ภายใน Project หนึ่งจะซ้ำกับของ Project อื่น

Project คือนามธรรมที่เป็นตัวแทนของ quota ของทรัพยากร ที่ผู้ใช้สามารถใช้สร้าง instances เช่น วีเอ็ม volume และ virtual network เป็นต้น ตัวอย่างของ quota ทรัพยากรภายใน Project ได้แก่ จำนวน vcpu cores ขนาด RAM รวมสำหรับสร้างวีเอ็ม ขนาดพื้นที่ storage สำหรับสร้าง volumes จำนวน virtual network จำนวน floating IP และ จำนวน security group เป็นต้น นอกจากนั้น ผู้ใช้ต้องมีสิทธิการใช้งาน Project ในระดับ member หรือมากกว่า เท่านั้นจึงจะสามารถใช้ทรัพยากรภายใน Project ได้

๑.1.1 ความสัมพันธ์ระหว่าง User Role Scope และ Policy

ระบบคีย์สโตนของโอเพนสแตคใช้วิธีการ Role-Based Access Control (RBAC) ในการบริหารจัดการสิทธิการเข้าใช้งานระบบโอเพนสแตค วิธีการ RBAC คือการพิจารณาสิทธิการใช้งานทรัพยากรจากการจับกลุ่ม keys สามอย่างประกอบไปด้วย (1) User (2) Role และ (3) Scope เข้าด้วยกันและใช้ combination ของ key เหล่านี้กำหนดสิทธิการใช้งานทรัพยากร (อ้างอิงเพจ Default Roles)

ในภาพ ๑-2 User คือนามธรรมของผู้ใช้ของระบบเพนสแตค ในรูปแบบของบัญชีผู้ใช้ (account) ผู้ใช้จะต้องผ่านการพิสูจน์ตัวตน (WHO เข้าใช้ระบบในภาพ) จึงจะสามารถใช้บัญชีของตนได้ User จะต้องถูกสร้างขึ้นภายใต้ Domain ใด Domain หนึ่งเสมอ ผู้ดูแลระบบสามารถนำ User หลาย User ภายใต้ Domain เดียวกันมารวมกันเป็น Group ซึ่งหมายถึงกลุ่มของ Users ที่ถ้าพิสูจน์ตัวตนแล้วว่าเป็นหนึ่งใน User ในกลุ่มก็จะผ่านการพิสูจน์ตัวตนของกลุ่ม หมายเหตุ: ในโอเพนสแตค ผู้ดูแลระบบสามารถกำหนดให้ User ที่ถูกสร้างใน Domain หนึ่งเป็น member ของ Project ใน Domain อื่นได้

Role คือนามธรรมของสิทธิในการใช้งานทรัพยากรของผู้ใช้ในโอเพนสแตค Role เหล่านี้เป็น string ของชื่อบทบาทที่ถูกสร้างขึ้นเพื่อสื่อความหมายให้เข้าใจกันโดยทั่วไป แต่กฎเกณฑ์ของทุกบทบาทจะถูกกำหนดอยู่ในนโยบาย (ซึ่งจะได้กล่าวถึงต่อไป) รายชื่อของ Role ในโอเพนสแตค ได้แก่

  1. admin คือบทบาทของผู้ดูแลระบบ

  2. manager คือบทบาทของผู้จัดการระบบ

  3. member คือบทบาทของผู้ใช้ระบบ

  4. reader คือบทบาทของผู้ดูที่สามารถ view instance มีอยู่ในระบบเท่านั้น

  5. บทบาทที่สร้างขึ้นใหม่หรือ custom ในภาพ เป็นบทบาทที่สร้างขึ้นเฉพาะกิจตามความต้องการพิเศษของผู้ใช้

  6. service เป็นบทบาทสำหรับ User ที่เป็นซอฟต์แวร์ส่วนประกอบของโอเพนสแตค เช่น โนวา นิวตรอน และอื่นๆ

ในภาพ ๑-2 บทบาท admin จะครอบคลุมความสามารถของบทบาท manager ซึ่งจะครอบคลุมความสามารถของ member ซึ่งจะครอบคลุมความสามารถของ reader ดังนั้นถ้า User มีความสามารถ admin ก็หมายความว่ามีความสามารถของ บทบาท manager member และ reader อยู่แล้ว

Scope คือนามธรรมของขอบเขตการใช้งานทรัพยากร สามระดับได้แก่

  1. System-scope คือการกำหนดค่า Identity ของการเข้าถึงทรัพยากรทั้งระบบ

  2. Domain-scope คือการกำหนดค่า Identity ของการเข้าถึงทรัพยากรของ Domain ในระบบ และ

  3. Project-scope คือการกำหนดค่า Identity ของการใช้งานชุดของทรัพยากรที่ถูกแบ่งย่อยภายใน Domain

ระบบคีย์สโตนรวมกลุ่ม User Role และ Scope เข้าด้วยกันเป็น (User, Role, Scope) Tuple เมื่อผู้ดูแลระบบออกคำสั่งทาง Web Interface หรือ CLI เพื่อกำหนดให้ User มี Role อะไรและใช้กับ Scope ใด (พร้อมทั้งระบุชื่อของ Scope นั้นด้วย) Tuple นั้นจะถูกใช้เป็น Combined Key สำหรับกำหนดสิทธิในการใช้งาน (Authorization)

สุดท้าย นโยบาย (หรือ Policies) คือการกำหนดกฎ Authorization ว่าแต่ละ Combined Key สามารถใช้งานฟังก์ชันใดของโอเพนสแตคได้บ้าง โอเพนสแตคใช้ไฟล์ /etc/COMPONENT/policy.json (โดยที่ COMPONENT หมายถึงชื่อ Component ของระบบโอเพนส‍แตค ได้แก่ keystone, glance, nova, neutron และ cinder เป็นต้น) เพื่อกำหนดกฎ Authorization ดังกล่าว

โอเพนสแตค อนุญาตให้ผู้ใช้เปลี่ยนกฎ Authorization ได้สองวิธีได้แก่ (1) ใช้ OpenStack CLI หรือ (2) แก้ไขไฟล์ policy.json โดยตรง

๑.1.2 บุคลิกภาพที่เกิดจากความสัมพันธ์ User Role Scope และ Policy

การสร้างความสัมพันธ์ของ (User, Role, Scope) Tuple ทำให้เกิดบุคลิกภาพ (Persona) 3 ระดับดังนี้ (อ้างอิง OpenStack Default Role และ Red Hat OpenStack Services on OpenShift)

1. Scope: ทั้งระบบ (หรือ System)

ใน Scope ระดับ System ผู้ดูแลระบบสามารถสร้างบุคลิกภาพดังต่อไปนี้

  1. บุคลิกภาพจากความสัมพันธ์ (User=admin, Role=admin, Scope=system) Tuple หมายถึงบัญชีผู้ใช้ชื่อ “admin” มีบทบาทเป็น admin ผู้ดูแลระบบของทรัพยากรทั้งหมด มีสิทธิใช้งานระบบตามกำหนดใน Policy คือ สามารถบริหารจัดการทุกสิ่งในระบบคีย์สโตน ยกตัวอย่างเช่น (1) สามารถเพิ่มหรือลบ Service (หรือ Component) ของโอเพนสแตค ซึ่งอนุมานความสามารถในการเข้าถึงเครื่องคอมพิวเตอร์และระบบเครือข่ายที่ใช้ติดตั้งระบบโอเพนสแตค (2) สามารถสร้างและจัดการ Service endpoint สำหรับติดต่อ Services ของโอเพนสแตค (3) สร้างและจัดการ Domain (4) สร้าง Federated Mapping (Map Identity ของระบบซอฟต์แวร์อื่นมายังของโอเพนสแตค) และ (5) ล้าง credentials ที่ค้างอยู่ในระบบ เป็นต้น

  2. บุคลิกภาพจากความสัมพันธ์ (User=userA, Role=member, Scope=system) Tuple หมายถึงบัญชีผู้ใช้ “userA” มีบทบาทเป็น member หรือสมาชิกของผู้ใช้ระบบ ในระดับทั้งระบบ มีสิทธิใช้งานระบบ (ตามกำหนดใน Policy) คือ สามารถ view ทุกสิ่งที่ระบบคีย์สโตนจัดการ ผู้ใช้ “UserA” สามารถ (1) ดูรายการของ Role ในระบบ (2) ดูรายการการกำหนด Role ให้กับผู้ใช้ (3) ดูรายการ Project (4) รายการกลุ่มผู้ใช้และสมาชิกในกลุ่ม เป็นต้น บุคลิกภาพนี้ใกล้เคียงกับของจากความสัมพันธ์ (User=userA, Role=reader, Scope=system) Tuple ต่างกันตรงที่ Role “reader” มีความสามารถในการ view น้อยกว่า

2. Scope: ระดับ Domain

ใน Scope ระดับ Domain ผู้ดูแลระบบสามารถสร้างบุคลิกภาพดังต่อไปนี้

  1. บุคลิกภาพจากความสัมพันธ์ (User=userB, Role=admin, Scope=domain) Tuple หมายถึงบัญชีผู้ใช้ชื่อ “userB” มีบทบาทเป็น admin ผู้ดูแลระบบภายใน Domain มีสิทธิใช้งานระบบ (ตามกำหนดใน Policy) คือ (1) สามารถจัดการสิ่งที่อยู่ภายใน Domain เกือบทุกเรื่อง (2) สามารถสร้าง Projects และ Users ภายใน Domain และ (3) สามารถตรวจสอบว่า User ที่ใช้ Project ที่อยู่ใน Domain นี้มี Role อะไรบ้าง

อย่างไรก็ตาม สิ่งที่ User ที่มีบุคลิกภาพนี้ไม่สามารถทำได้เกี่ยวกับ Domain ที่มันอยู่ มีดังนี้

  1. ไม่สามารถลบหรือ Disable Domain ที่มันอยู่ได้ เนื่องจากผู้สร้างคือ admin ในระดับ System

  2. ไม่สามารถเข้าถึงทรัพยากร เช่น คอมพิวเตอร์และระบบเครือข่ายที่ใช้ติดตั้งโอเพนสแตค และ

  3. ไม่สามารถเปลี่ยนแปลง Configuration เกี่ยวกับการใช้งานทรัพยากรภายใน Domain เนื่องจากเป็นสิ่งที่ทำได้ในระดับ System เท่านั้น

มาตรการป้องกันความผิดพลาด: ใน admin role แบบดั้งเดิม (Legacy) โอเพนสแตคเปิดช่องให้ผู้ใช้ที่มี Role admin ระดับ Domain สามารถขยายสิทธิ์การเข้าถึง (Privilege Escalation) เป็นRole admin ในระดับ System ได้ ถ้าผู้ดูแลระบบในระดับ System ไม่ทราบหรือกำหนดค่า Configuration ของระบบคีย์สโตนผิดพลาด จะทำให้ admin ระดับ Domain สามารถเข้าถึงและจัดการทรัพยากรนอก Domain โดยไม่คาดคิดได้ (อ้างอิง domain manager github) ด้วยเหตุนี้ ผู้พัฒนาระบบคีย์สโตนจึงได้สร้าง Role manager ของ Domain ขึ้นเพื่อป้องการความผิดพลาดนี้ ซึ่งจะกล่าวถึงต่อไป

  1. บุคลิกภาพจากความสัมพันธ์ (User=userC, Role=manager, Scope=domain) Tuple หมายถึงบัญชีผู้ใช้ชื่อ “userC” มีบทบาทเป็น manager ผู้จัดการระบบภายใน Domain มีสิทธิใช้งานระบบ (ตามกำหนดใน Policy) คือสามารถบริหารจัดการทรัพยากรที่เกี่ยวข้องกับ Identity ภายใน Domain เท่านั้น ยกตัวอย่างเช่น สร้างและเปลี่ยนแปลง Users Projects และ Groups ภายใน Domain และสามารถสร้างและยกเลิก Roles ที่ใช้ใน Domain และสามารถเรียกดูความสัมพันธ์ระหว่าง Roles และ Identity ภายใน Domain เป็นต้น

Domain manager role ไม่สามารถจัดการการใช้งานทรัพยากรได้เหมือนกับ Domain admin role ถึงแม้ว่า Domain manager จะสามารถกำหนดหรือเปลี่ยนแปลง Role ของ User ได้แต่ก็มีข้อจำกัด ที่ไม่สามารถเปลี่ยนแปลงสิ่งที่กำหนดโดย Domain admin และไม่สามารถกำหนดหรือเปลี่ยน Role ของ User ใน Domain ให้เป็น Role admin ได้

  1. บุคลิกภาพจากความสัมพันธ์ (User=userD, Role=member, Scope=domain) และ Tuple หมายถึง “userD” เป็นสมาชิกของ Domain ที่สามารถ view ทรัพยากรและข้อมูล metadata ภายใน Domain เท่านั้น ส่วนบุคลิกภาพจากความสัมพันธ์ (User=userD, Role=reader, Scope=domain) ก็คล้ายกันกับ Role member เพียงแต่สามารถดูข้อมูลได้น้อยกว่า ทั้งสองแบบเหมาะสมกับการ Monitor หรือ Audit การใช้งานทรัพยากรภายใน Domain

3. Scope: ระดับ Project

User ใน Project Scope มีความแตกต่างจาก User ในระดับ System และ Domain คือ User ใน Project Scope เท่านั้นสามารถใช้งาน (หรือ consume) ทรัพยากรภายใต้โควตาของ Project ได้ ในขณะที่ User ในระดับ System และ Domain ไม่ว่าจะมี Role เป็นอะไรก็ไม่สามารถใช้งานทรัพยากรใน Project ได้

ใน Project Scope ผู้ดูแลระบบสามารถสร้างบุคลิกภาพให้ User ดังต่อไปนี้

  1. บุคลิกภาพจากความสัมพันธ์ (User=admin, Role=admin, Scope=project) Tuple หมายถึงบัญชีผู้ใช้ชื่อ “admin” มีบทบาทเป็น admin (หรือผู้ดูแลระบบ) ภายใน Project ซึ่งตาม Default Policy ของโอเพนสแตคมีสิทธิใช้งานระบบดังนี้

    1. สร้าง เพิ่ม/ลด User และ Group ที่สามารถใช้งาน Project

    2. สร้างและจัดการทรัพยากรใน Project และ

    3. แชร์ทรัพยากรภายใน Project กับ Project อื่น แต่ไม่สามารถ view หรือจัดการทรัพยากรในระดับ System หรือ Domain scope ได้

User ที่มี Role แบบ admin สามารถทำทุกอย่างที่ Role member ทำได้

  1. บุคลิกภาพจากความสัมพันธ์ (User=userE, Role=member, Scope=project) Tuple หมายถึงบัญชีผู้ใช้ชื่อ “userE” มีบทบาทเป็น member (หรือสมาชิกของ) Project มีสิทธิใช้งานทรัพยากรภายใต้ Quota ที่กำหนด เช่นสร้างและใช้งานวีเอ็ม Volume Security Groups virtual network และ virtual router เป็นต้น User มี Role แบบ member สามารถทำทุกอย่างที่ Role reader ทำได้

  2. บุคลิกภาพจากความสัมพันธ์ (User=userE, Role=reader, Scope=project) Tuple หมายถึงบัญชีผู้ใช้ชื่อ “userE” มีบทบาทเป็น reader ที่สามารถอ่านหรือดูข้อมูลเกี่ยวกับการใช้งานทรัพยากรภายใน Project ได้อย่างเดียว แต่ไม่สามารถใช้งานหรือจัดการได้เหมือน Role member และ admin

๑.1.3 การสร้างบุคลิกภาพของเริ่มต้นของ User เมื่อติดตั้งโอเพนสแตค

เมื่อติดตั้งโอเพนสแตค ระบบคีย์สโตนจะรัน keystone-manage bootstrap operation ซึ่งจะทำสิ่งต่อไปนี้ (อ้างอิง Keystone 11.0.1 Configuration)

  1. สร้าง Default domain

  2. สร้าง User “admin” และ Project “admin” ใน default domain

  3. สร้าง Role “admin” เป็น Role แรกในระบบโอเพนสแตค (หมายเหตุ: Role เป็นนามธรรม Global )

  4. สร้าง (User=admin, Role=admin, Scope=project) Tuple และสร้าง Policy ให้ admin user ใน Default domain เป็นผู้ดูแลระบบของ Project “admin” และสามารถใช้ทรัพยากรใน Project ภายในปริมาณที่กำหนดใน Quota เพื่อสร้างวีเอ็มและ Instance ชนิดอื่นได้

  5. สร้าง (User=admin, Role=admin, Scope=system) Tuple ซึ่งเป็นการกำหนดให้ admin user ใน Default domain เป็นผู้ดูแลระบบที่สามารถติดตั้ง เปลี่ยนแปลง configuration ของระบบโอเพนสแตคและสามารถจัดการทรัพยากรที่ใช้ติดตั้งระบบฯได้

ระบบคีย์สโตนจะกำหนดความสัมพันธ์ (User=admin, Role=admin, Scope=project) และ (User=admin, Role=admin, Scope=system) tuples พร้อมทั้งกฎการกำหนดสิทธิ์ (Authorization Rules) ในไฟล์ policy อันจะส่งผลให้ admin user สามารถเข้าถึงทรัพยากรคอมพิวเตอร์และระบบเครือข่ายเพื่อติดตั้งและจัดการ Identity และ Service ทุกอย่างของโอเพนสแตคได้ ในขณะเดียวกัน admin user ก็สามารถสร้างวีเอ็มและ Instance อื่นภายใน Project admin ได้ด้วย หลังจากนั้น User admin สามารถสร้าง User Role Project และ Domain เพิ่มเติมได้ตามต้องการ

๑.2 การใช้งานด้วย Dashboard

Note

หนังสือฉบับนี้เน้นบรรยายการใช้งานหลังการติดตั้ง แทนที่จะเป็นคู่มือการใช้งานซึ่งสามารถอ่านเพิ่มเติมได้จาก (1) OpenStack Documentation และ (2) OpenStack Operations Guide

หลังจากติดตั้ง ผู้ใช้โอเพนสแตคสามารถเข้าใช้งานระบบได้ทางยูอาร์แอล http://<virtual IP address>/horizon โดยที่ <virtual IP address> คือ IP address ที่ผู้ใช้สามารถเข้าถึง OpenStack Dashboard หลังจากติดตั้ง (ยกตัวอย่างเช่น จากการติดตั้งในบทที่ ๐ ยูอาร์แอลนี้คือ http://172.16.81.254/horizon) ซึ่งผู้ใช้จะเห็นหน้าล็อคอินดังภาพ ๑-3

ในขณะที่ติดตั้งโอเพนสแตค ซอฟต์แวร์ที่ใช้ติดตั้ง (Kolla Ansible) จะสร้างบัญชีผู้ใช้ admin และพาสเวิร์ดของบัญชีนั้นให้ บัญชี admin มีบทบาทเป็นผู้ดูแลระบบ (System Administrator) และเป็นสมาชิก (Member) จะมี Admin Project ในภาพที่ ๑-1 เราจะล็อกอินเข้าสู่ Project admin (หมายเหตุ: หนังสือเล่มนี้สมมุติว่าระบบโอเพนสแตคมี Domain ที่ใช้งานเพียง Domain เดียวคือ default domain เท่านั้น)

หลังจากล็อกอินผู้ใช้ admin จะพบหน้าเว็บเพจในภาพ ๑-2 ซึ่งด้านขวาของภาพแสดงข้อมูลสรุปการใช้งานทรัพยากรในภาพรวมที่ผู้ใช้มีสิทธิใช้ได้ตาม quota ชนิดของทรัพยากรที่รายงานในเพจนี้มีสามชนิด ได้แก่ ทรัพยากรสำหรับประมวลผล (Compute) ทรัพยากรหน่วยเก็บข้อมูล Volume (Volume) และทรัพยากรระบบเครือข่าย (Network) นอกจากนั้นผู้ใช้ยังสามารถเรียกดูสถิติการใช้งานทรัพยากรในรายละเอียดตามช่วงเวลาจากส่วน “Usage Summary” ของเพจได้ด้วย สำหรับรายละเอียดของทรัพยากร จะกล่าวถึงอีกครั้งเมื่อแสดงการสร้างทรัพยากรเสมือนแบบต่างๆเพื่อใช้งาน ด้านซ้ายของภาพ ๑-2 แสดงแท็บที่รวบรวมข้อมูลและฟังก์ชันการปฏิบัติงาน 3 หมวดหมู่ได้แก่

  1. แท็บ Project รวมฟังก์ชันการจัดการทรัพยากรสำหรับ Project ของผู้ใช้ จากตัวอย่างในภาพคือ Admin Project ในภาพแสดงแท็บย่อยของแท็บ Project ได้แก่ API Access Compute Volume และ Network และภายใต้แท็บย่อย Compute แสดงแท็บย่อย Overview Instances Images Key Pairs และ Server Groups

  2. แท็บ Admin รวมฟังก์ชันสำหรับจัดการทรัพยากรของทุก Project ในระบบโอเพนสแตค ผู้ใช้ที่เป็นผู้ดูแลระบบเท่านั้นที่เห็นและสามารถใช้งานแท็บนี้ได้

  3. แท็บ Identity รวมฟังก์ชันสำหรับจัดการ Profile และรายการผู้ใช้ใน Project เดียวกันกับของบัญชีผู้ใช้ที่ล็อกอิน ในกรณีที่ผู้ใช้เป็นผู้ดูแลระบบ แท็บนี้จะแสดงฟังก์ชันสำหรับจัดการ Profile ผู้ใช้ของทุก Project

จากภาพ ๑-2 ภายใต้แท็บ Project จะมีแท็บย่อยที่เป็นตัวแทนฟังก์ชันการปฏิบัติงานของโอเพนสแตค 4 แท็บได้แก่

  1. API Access แสดง URL endpoints ของ OpenStack Service และสคริปต์สำหรับให้ผู้ใช้ดาวน์โหลดเพื่อใช้คำสั่ง Command Line

  2. Compute แสดงข้อมูลและคำสั่งที่เกี่ยวข้องกับวีเอ็ม เมื่อกดแท็บ Compute จะมีเมนูปรากฏดังภาพ ๑-3 ได้แก่รายการ VM instance รายการ image template รายการ key pairs รายการ server groups

  3. Volume (Volume) เมื่อกดแท็บ Volumes จะมีเมนูปรากฏดังภาพ ๑-3 ซึ่งจะแสดงรายการหน่วยเก็บข้อมูลเสมือน (Volume) และรายการ Snapshot (Snapshots) รายการกลุ่มของ Volume (Group) และรายการกลุ่มของ Snapshot (Group Snapshots)

  4. เน็ตเวิร์ค (Network) เมื่อกดแท็บ Network จะมีเมนูปรากฏดังภาพ ๑-3 แสดง Topology ของระบบเครือข่าย (Network Topology) รายการระบบเครือข่ายสเมือน (Network) รายการของเร้าเตอร์ (Router) และรายการของ Floating IP

ภายใต้แท็บ Admin ในภาพ ๑-2 ซึ่งเป็นแท็บที่จะปรากฏเฉพาะที่หน้า Dashboard ของผู้ใช้ที่มีบทบาทเป็นผู้ดูแลระบบเท่านั้น (ผู้ใช้ที่เป็นสมาชิกธรรมดาจะไม่เห็นแท็บนี้) เมื่อกดแท็บ Admin จะมีแท็บย่อยสี่แท็บได้แก่ compute, volume, network และ system ซึ่งเมื่อเลือกแท็บย่อยสามแท็บย่อยแรกจะแสดงรายการฟังก์ชันดังเมนูด้านซ้ายสุดของภาพ ๑-4 ซึ่งเมื่อกดแท็บย่อยเหล่านั้น OpenStack Dashboard จะแสดงเมนูย่อยลงไปอีกดังภาพ เมนูเหล่านี้แสดงข้อมูลการใช้งานทรัพยากรรวมของทุก Project และฟังก์ชันสำหรับจัดการกับทรัพยากรเหล่านั้น (ซึ่งจะไม่บรรยายรายละเอียดในหนังสือเล่มนี้)

๑.2.1 การเพิ่ม Project และผู้ใช้

ในอันดับถัดไป จะบรรยายการสร้าง Project และผู้ใช้ใหม่ในระบบโอเพนสแตค โดยที่ผู้ใช้ Admin ซึ่งเป็นผู้ดูแลระบบจะเป็นผู้สร้างด้วยการใช้แท็บIdentity เมื่อกดขยายแล้วจะได้แท็บย่อยดังภาพที่ ๑-5 ซึ่งประกอบไปด้วยแท็บ Project (Projects) แท็บผู้ใช้ (Users) แท็บกลุ่ม (Groups) แท็บบทบาท (Roles) และแท็บ Application Credentials เนื่องจากในบทนี้จะบรรยายการใช้งานระบบเบื้องต้น ดังนั้นจะยังไม่อธิบายการใช้งานแท็บกลุ่มกับแท็บ Application Credentials ในกรณีที่ผู้ใช้ไม่ใช่ผู้ดูแลระบบ แท็บ Identity จะประกอบไปด้วย แท็บย่อย Project ผู้ใช้ กลุ่ม และ Application Credentials เท่านั้น

ในภาพ ๑-6 เมื่อผู้ดูแลระบบเลือกแท็บย่อย Project (ลูกศรสีแดง) ระบบจะแสดงรายการผู้ใช้ที่มีอยู่ในปัจจุบัน หลังจากนั้นเมื่อกดปุ่ม Create Project ระบบก็จะแสดงรายการดังภาพ ๑-7

หลังจากนั้น ผู้ดูแลระบบจะใส่ชื่อ Project Project-A ซึ่งจะอยู่ใน default domain ของระบบโอเพนสแตค และกดปุ่ม Project Member ระบบจะแสดงเว็บเพจเพื่อให้ผู้ดูแลระบบเลือกสมาชิกของผู้ใช้ของ Project นี้ ดังภาพ ๑-8 ซึ่งในขั้นตอนนี้เราจะยังไม่เลือกเนื่องจากยังไม่ได้สร้างผู้ใช้สำหรับ Project นี้ (วัตถุประสงค์ของการแสดงหน้านี้คือเพื่อให้ผู้อ่านรู้จักหน้าเว็บเพจสำหรับเพิ่มผู้ใช้ใน Project ในอนาคต)

สุดท้าย ผู้ดูแลระบบจะต้องกดปุ่ม Create Project ในภาพ ๑-7 เพื่อสร้าง Project-A ถัดจากนั้นระบบจะแสดงภาพรายการ Project ทั้งหมด ดังภาพ ๑-9

หลังจากสร้าง Project แล้ว ต่อไปผู้ดูแลระบบจะกำหนด quota ของทรัพยากรของ Project-A โดยกดปุ่มขยายเมนูตรงปุ่ม “Manage Member” (ลูกศรในภาพ ๑-9) และจะได้เมนูในภาพ ๑-10 และผู้ดูแลระบบจะเลือกปุ่ม “Modify Quotas” หลังจากนั้นระบบจะแสดงหน้าเว็บในภาพ ๑-11

ในภาพ ๑-10 ผู้ดูแลระบบจะกำหนดค่าพารามิเตอร์ (Parameters) quota ของทรัพยากรสำหรับการประมวลผล ซึ่งผู้ใช้ของ Project นี้จะไม่สามารถใช้ทรัพยากรเกินจำนวนที่ระบุใน quota ได้ รายการพารามิเตอร์ของทรัพยากรที่สำคัญ ที่ผู้ดูแลระบบจะกำหนดค่าในตัวอย่างนี้ มีดังต่อไปนี้

  • Instance: จำนวน VM instance ที่ Project นี้จะมีได้

  • VCPUs: จำนวนซีพียูคอร์โดยรวมของทุกวีเอ็มใน Project

  • RAM: ขนาดหน่วยความจำโดยรวม (หน่วยเป็น MB)

  • Key Pairs: จำนวนคู่ Public และ Private Keys ที่ผู้ใช้สามารถสร้างเพื่อใช้ล็อกอินเข้าสู่วีเอ็มใน Project

สำหรับค่าอื่นๆนั้น ผู้ดูแลระบบจะยังไม่กำหนดค่าหรือใช้งานในตัวอย่างนี้ ผู้ใช้สามารถดูข้อมูลเพิ่มเติมได้จาก (https://docs.openstack.org/python-openstackclient/latest/cli/command-objects/quota.html)

ถัดจากนั้น ผู้ดูแลระบบจะกดปุ่ม “Volume” (ดังภาพ ๑-12) เพื่อกำหนด quota ของการเก็บข้อมูลในหน่วยเก็บข้อมูลแบบบล็อก (Block Storage) ดังนี้

  • Volumes หมายถึงจำนวน Volume ของ Block Storage ที่สร้างได้ใน Project

  • Volume Snapshots คือจำนวนสำเนา Snapshot โดยรวมที่สร้างได้ใน Project

  • Total Size of Volume and Snapshots คือขนาดโดยรวมของ Volume และ Snapshot (หน่วยเป็น GiB)

เมื่อผู้ดูแลระบบกดปุ่ม “Network” (ดังภาพ ๑-13) ก็จะเข้าสู่หน้าเว็บสำหรับกำหนดค่า quota พารามิเตอร์ของทรัพยากรที่เกี่ยวข้องกับการสื่อสาร ได้แก่

  • Networks คือจำนวนระบบเครือข่ายภายในที่สร้างขึ้นได้ใน Project

  • Subnets คือจำนวนซับเน็ตโดยรวมของทั้ง Project

  • Ports คือจำนวน Network Ports โดยรวมที่มีได้ใน Project

  • Routers คือจำนวนเร้าเตอร์เสมือนโดยรวมของทั้ง Project

  • Floating Ips คือจำนวน Floating IP โดยรวมของทั้ง Project

  • Security Groups จำนวนกลุ่มของกฎของการรักษาความปลอดภัยที่มีได้ใน Project

  • Security Group Rules คือจำนวนกฎสำหรับการรักษาความปลอดภัยโดยรวมของทั้ง Project

ในการสร้างผู้ใช้ของ Project Project-A ผู้ดูแลระบบต้องกดแท็บย่อย Users ในภาพ ๑-6 ระบบจะแสดงเว็บเพจดังภาพ ๑-14

หลังจากนั้น ผู้ดูแลระบบจะเลือกแท็บย่อย Users ดังภาพ ๑-14 และกดปุ่ม “Create User” แล้วระบบจะแสดงหน้าเว็บดังภาพ ๑-15 และ ๑-16 ซึ่งผู้ดูแลระบบจะใส่ข้อมูล username เป็น “A-user” ป้อนพาสเวิร์ดเป็น “A-user” และกำหนดให้ผู้ใช้นี้เป็นสมาชิกของ Project Project-A และให้มีบทบาทเป็น “User” และกดปุ่ม “Create User”

๑.2.2 การสร้าง cirros VM instance

ในการสร้างวีเอ็มขึ้นใช้งานผู้ใช้ A-user จะล็อกอินเข้าสู่ Project-A ดังภาพ ๑-17 หลังจากนั้น ผู้ใช้จะเลือกแท็บ “Project” เลือกแท็บย่อย “Compute” และเลือกแท็บย่อย “Instances” ระบบจะแสดงหน้าเว็บแสดงรายการของวีเอ็มของ Project Project-A ซึ่งยังไม่มีวีเอ็ม ดังภาพ ๑-18

หลังจากผู้ใช้กดปุ่ม “Launch Instance” ในภาพ ๑-18 เพื่อสร้างวีเอ็ม ระบบจะแสดงหน้าเว็บดังภาพ ๑-19 ซึ่งผู้ใช้จะระบุชื่อวีเอ็มคือ “cirros-1” เนื่องจากเราจะสร้างวีเอ็มแบบพื้นฐานที่สุดที่ใช้เกสต์โอเอส cirros ซึ่งสคริปต์ติดตั้งได้เตรียมอิมเมจไว้ให้แล้วตั้งแต่ตอนติดตั้ง (https://github.com/cirros-dev/cirros) (หมายเหตุ ผู้ใช้สามารถตั้งชื่อวีเอ็มอย่างไรก็ได้) เมื่อกำหนดชื่อและจำนวนเสร็จแล้วให้กด “Next”

ระบบจะแสดงหน้าเว็บเพจดังภาพ ๑-20 ขอให้สังเกตว่า หน้าเว็บเพจจะถามผู้ใช้ว่าต้องการจะสร้าง Volume ใหม่หรือไม่ (ดู “Create New Volume”) ซึ่งระบบโอเพนสแตคจะมีทางเลือกให้ผู้ใช้ 2 ทางเลือก ได้แก่

  1. ผู้ใช้สร้าง Volume ใหม่ (ภายใต้การจัดการของ Component ซินเดอร์) สำหรับเก็บ Boot Image ซึ่งหลังจากที่ผู้ใช้เลิกใช้งานวีเอ็มและลบวีเอ็มออกจากระบบแล้ว ผู้ใช้สามารถเอาข้อมูลใน Volume ไปใช้งานหรือแม้กระทั่งบูทวีเอ็มอื่นได้ในภายหลัง

  2. ผู้ใช้กำหนดให้โนวาใช้พื้นที่ใน Local Storage ของเครื่อง compute host ที่โนวารันวีเอ็มสำหรับเก็บ Boot Image ในทางเลือกนี้เมื่อผู้ใช้ลบวีเอ็ม Boot Image และข้อมูลในนั้นจะถูกลบไปด้วย

ในภาพ ๑-20 ขอให้สังเกตว่า ค่าทางเลือกในช่อง “Create New Volume” จะมีค่าดีฟอลต์ (Default) เป็น“Yes” หมายความว่าโดยดีฟอลต์ระบบจะใช้พื้นที่ Volume เพื่อเก็บ Boot Image ของเกสต์โอเอส และในบรรทัดถัดไประบบจะถามว่าผู้ใช้ต้องการสร้าง Volume ขนาดเท่าไร ซึ่งผู้ใช้จะต้องประมาณขนาดให้เหมาะสมกับขนาดของเกสต์โอเอสที่ตนจะใช้งาน (ใช้ “1 GB” ในภาพ หรือเปลี่ยนเป็นค่าอื่น) และเลือกว่าจะลบ Volume เมื่อลบ (Delete) วีเอ็มออกจากระบบโอเพนสแตคหรือไม่ ซึ่งเรากำหนดให้ค่าเป็น “No” ตามค่าดีฟอลต์

ในภาพ ๑-21 ถ้าผู้ใช้เลือกที่จะไม่ใช้ Volume ระบบก็จะใช้ทางเลือกที่ 2 และแสดงเว็บเพจดังภาพ (หมายเหตุ ในตัวอย่างการสร้างวีเอ็ม cirros-1 นี้ เราจะกำหนดให้วีเอ็มใช้พื้นที่ดิสก์บน compute host เพื่อเก็บ Boot Image )

ในช่อง “Select Boot Source” ผู้ใช้สามารถเลือกได้ว่าจะใช้ Disk Image จากแหล่งใดแหล่งหนึ่งต่อไปนี้ (หมายเหตุ ในตัวอย่างของการสร้างวีเอ็ม cirros-1 นี้ ผู้ใช้จะเลือก image เป็น Boot Source)

  1. Image หมายถึงให้โนวาอ่านข้อมูลของอิมเมจจาก image template ที่เก็บไว้ใน Repository ของ Component แกลนซ์ ของโอเพนสแตค ไปยังพื้นที่ๆจะใช้เก็บ Boot Image ของวีเอ็ม ในกรณีที่ผู้ใช้จะสร้าง Volume เพื่อเก็บ Boot Image ของวีเอ็ม โอเพนสแตคจะสร้างพื้นที่ใน Volume แล้วทำสำเนาของอิมเมจจากแกลนซ์ไปยังพื้นที่ Volume นั้น แต่ถ้าผู้ใช้ไม่สร้าง Volume และใช้พื้นที่ดิสก์ของเครื่อง compute host โอเพนสแตคจะทำสำเนาของ Disk Image จากแกลนซ์ไปยัง Local Storage ของเครื่อง compute host ที่จะรันวีเอ็ม

  2. Image snapshots หมายถึงการอ่านข้อมูลจาก Snapshot ของ Disk Image ที่เก็บอยู่ใน Repository ของแกลนซ์ แทนที่จะอ่านจาก image template ธรรมดาเหมือนในกรณีแรก โอเพนสแตคจะทำสำเนาของ Snapshot อิมเมจไปยังพื้นที่ๆผู้ใช้เลือกที่จะใช้เก็บ Boot Image ของวีเอ็มเหมือนในกรณีแรก

  3. Volume หมายถึงผู้ใช้มี Volume ที่เป็น Boot Image อยู่ใน Block Storage ที่จัดการโดย Component ซินเดอร์ของโอเพนส‍แต‍คอยู่แล้ว และจะเลือกใช้ Volume นั้นให้เป็น Boot Image ในกรณีที่ผู้ใช้เลือกทางเลือกนี้ โอเพนสแตคจะไม่สร้าง Volume ใหม่และไม่สร้างพื้นที่สำหรับสร้าง Boot Image ของวีเอ็มใหม่ และไม่ต้องทำสำเนาของเกสต์โอเอสอิมเมจแต่อย่างใด

  4. Volume Snapshots นั้นเหมือนกับกรณีเลือกใช้ Volume แต่เปลี่ยนเป็นใช้ Volume Snapshots ที่ผู้ใช้สร้างไว้ก่อนหน้าแทน

เนื่องจากตอนนี้เรามีเพียง Disk Image ของเกสต์โอเอส cirros อย่างเดียวเป็น Template ใน Repository ของ Component แกลนซ์ (ภาพ ๑-22) ระบบจึงแสดง cirros เป็นรายการเดียวและเราจะเลือกโอเอสนี้เป็นเกสต์โอเอสอิมเมจของวีเอ็ม หลังจากนั้นผู้ใช้กด “Next” และระบบจะแสดงเว็บเพจให้ผู้ใช้เลือก Flavor ซึ่งหมายถึง Specification หรือ Spec ของวีเอ็ม (ภาพ ๑-23) ซึ่งในขั้นตอนของการติดตั้งระบบได้มีการสร้างไว้สอง Flavor ได้แก่ 1) m1.nano คือ Spec ของวีเอ็มที่มีจำนวน ซีพียูคอร์เสมือน 1 คอร์ มีขนาดของหน่วยความจำ 64 GB และขนาดฮาร์ดดิสก์ 1 GB และ 2) m1.mini เป็น Spec ของวีเอ็มที่มีซีพียูคอร์เสมือน 1 คอร์ มีขนาดหน่วยความจำ 512 MB และขนาดของ Boot Image 1 GB

ในตัวอย่างนี้เราจะเลือก Flavor m1.mini เพื่อรัน cirros-1 ถัดจากนั้นผู้ใช้จะกด “Next”

ในภาพ ๑-24 ระบบแสดงเว็บเพจให้ผู้ใช้เลือกว่าจะเชื่อมต่อวีเอ็มเข้ากับระบบเครือข่ายเสมือนใด แต่เนื่องจากในระบบตั้งต้น ระบบเครือข่ายที่ทุก Project สามารถเข้าถึงได้คือระบบเครือข่ายจากผู้ให้บริการที่เชื่อมต่อระบบเครือข่ายภายนอกกับระบบเครือข่ายเสมือนภายในของโอเพนสแตค ซึ่งในปัจจุบันยังไม่มี และจะถูกสร้างขึ้นภายหลัง ดังนั้นในตัวอย่างนี้ เราจะเชื่อมต่อ cirros-1 เข้ากับระบบเครือข่ายของผู้ให้บริการหรือ provider1 ในภาพ (ในกรณีที่ไม่สามารถเชื่อมต่อกับระบบเครือข่ายของผู้ให้บริการโดยตรง ผู้ใช้จะต้องสร้างระบบเครือข่ายภายในเสมือนและเร้าตอร์เสมือนก่อน)

หลังจากนั้นผู้ใช้กด “Next” และระบบจะแสดงหน้าเว็บเพจในภาพ ๑-25 ซึ่งจะแสดงกลุ่มของกฎของการรักษาความปลอดภัย (Security groups) ของ Project Project-A (แต่ละ Project มีกฎเหล่านี้ของตนเอง)​ ซึ่งก็คือกลุ่มของกฎไฟร์วอล (Firewalls) นั่นเอง ซึ่งในเบื้องต้นมีอยู่กลุ่มเดียวคือ กลุ่มรักษาความปลอดภัยดีฟอลต์​ (Default Security Groups) ผู้ใช้สามารถสร้างกลุ่มเพิ่มขึ้น หรือเพิ่มกฎในกลุ่มดีฟอลต์ ก็ได้ถ้าต้องการเปลี่ยนแปลงกฎในภายหลัง อย่างไรก็ตามในกลุ่มความปลอดภัยดีฟอลต์นี้ ระบบจะอนุญาตให้วีเอ็มเริ่มการสร้างช่องทางเชื่อมต่อเพื่อสื่อสารข้อมูลจากวีเอ็มออกสู่โลกภายนอกได้เท่านั้น

ถัดจากนั้น ผู้ใช้กดปุ่ม “Launch Instance” เพื่อสร้างวีเอ็มและรันวีเอ็มในระบบโอเพนสแตค หลังจากกดปุ่ม ระบบจะแสดงหน้าจอในภาพ ๑-26 ซึ่งระบบจะแสดงว่าได้สร้างและรันวีเอ็ม cirros-1 แล้ว โดยที่วีเอ็มจะถูกกำหนดให้เชื่อมต่อกับ ระบบเครือข่ายเสมือน provider1 ผ่าน NIC ที่หนึ่งของวีเอ็มและมีค่าไอพีคือ 192.168.20.172

๑.2.3 การใช้งาน cirros VM instance ทางคอนโซล

วิธีการพื้นฐานที่สุดในการเข้าใช้งานวีเอ็มคือการเข้าใช้งานผ่านคอนโซล ผู้ใช้ต้องกดปุ่มเมนูถัดจากปุ่ม “Create Snapshot” และจะเห็นเมนูดังภาพ ๑-27 ผู้ใช้จะเลือกตัวเลือก console ระบบจะแสดงหน้าเว็บเพจดังภาพ ๑-28 ผู้ใช้จะต้องนำเคอร์เซอร์ไปวางบนแถบสีน้ำเงินด้านบนของหน้าจอคอนโซล แล้วเลื่อนกลับเข้ามาในคอนโซล หลังจากนั้นผู้ใช้จะสามารถล็อกอินเข้าสู่เครื่อง cirros-1 โดยป้อนชื่อบัญชี เป็น “cirros” และพาสเวิร์ด “gocubsgo”

ในภาพ ๑-29 เมื่อล็อกอินเข้าสู่วีเอ็มแล้ว ผู้ใช้สามารถทดสอบระบบเครือข่ายโดยสั่ง “ping www.google.com” เพื่อทดสอบว่าวีเอ็มสามารถติดต่อ DNS server ที่ไอพี 8.8.8.8 ได้และสามารถติดต่อกับอินเตอร์เน็ตได้

อย่างไรก็ดี ภาพ ๑-30 แสดงการป้องกันการเข้าถึงวีเอ็มที่ไม่ได้รับอนุญาต ทำให้ผู้ใช้ไม่สามารถใช้ซอฟต์แวร์ ssh client ล็อกอินทางไกลจากระบบเครือข่ายภายนอกระบบโอเพนสแตคเข้าสู่วีเอ็ม cirros-1 ซึ่งมีค่าไอพีคือ 192.168.20.172 ได้ และไม่สามารถใช้ ping ไอพีนี้ได้ด้วย ทั้งนี้เป็นเพราะไฟร์วอลของระบบโอเพนสแตคป้องการการเข้าถึงไว้ หากผู้ใช้ต้องการให้วีเอ็มของตนเข้าถึงได้จากระบบเครือข่ายภายนอก ผู้ใช้จะต้องปรับเปลี่ยนกฎในกลุ่มกฎรักษาความปลอดภัยที่จะได้กล่าวถึงต่อไป

๑.2.4 การเปลี่ยนแปลงกฎไฟร์วอลโดยเปลี่ยนแปลงค่าในกลุ่มกฎรักษาความปลอดภัย

ในระบบโอเพนสแตค กลุ่มของกฎรักษาความปลอดภัย (security groups) เป็นเสมือนปราการป้องกันการเข้าถึงวีเอ็มของโอเพนสแตคที่บังคับให้ทุกวีเอ็มใช้ข้อกำหนดค่าในกลุ่มกฎรักษาความปลอดภัยแบบดีฟอลต์ (default security group) เป็นค่าตั้งต้นโดยอัตโนมัติ

เนื่องจากกลุ่มดีฟอลต์อนุญาตให้วีเอ็มเริ่มต้นการสื่อสารสู่ภายนอกได้เท่านั้น เราจึงไม่สามารถล็อกอินทางไกล (remote login) เข้าถึงวีเอ็มได้ดังภาพที่ ๑-30 ผู้ใช้สามารถแก้ปัญหานี้ได้สองวิธี วิธีแรก ผู้ใช้สามารถสร้างกลุ่มของกฎรักษาความปลอดภัยขึ้นใหม่ แล้วเพิ่มกฎในกลุ่มใหม่เพื่ออนุญาตให้

  1. ผู้ใช้สามารถล็อกอินทางไกลจากคอมพิวเตอร์อื่นผ่านระบบเครือข่ายได้ด้วย SSH Protocol หรือเปิดให้มีการสื่อสารผ่านพอร์ต 22 ได้นั่นเอง

  2. ผู้ใช้สามารถส่งข้อความแบบ ICMP จากคอมพิวเตอร์อื่นผ่านระบบเครือข่ายเข้าสู่วีเอ็มได้ หรือเปิดรับข้อความที่มีเลขที่โพรโตคอลเท่ากับ 1 นั้นเอง (https://datatracker.ietf.org/doc/html/rfc792)

หรือ ผู้ใช้อาจทำวิธีที่สองคือ เพิ่มกฎทั้งสองข้างต้นใน กลุ่มดีฟอลต์ ซึ่งวิธีการที่สองจะสร้างผลกระทบกับทุกวีเอ็มใน Project และสามารถทำได้หลังจากเรียนรู้วิธีการที่หนึ่งแล้ว ดังนั้นจะแสดงวิธีการที่หนึ่งเท่านั้น

ในการเพิ่มกลุ่มของกฎ ผู้ใช้ต้องกดแท็บ Network แล้วกดแท็บย่อย Security Group แล้วกดปุ่ม Create Security Group ดังภาพ ๑-31

หลังจากนั้นใส่ชื่อกลุ่มใหม่ว่า SSH-ICMP และกดปุ่ม Create Security Group ระบบจะแสดงหน้าเว็บเพจในภาพ ๑-32 ซึ่งแสดงกฎตั้งต้นของกลุ่มรักษาความปลอดภัยที่เหมือนกับกฎดีฟอลต์ของระบบ ในภาพ ๑-33 เมื่อกดปุ่ม Add Rules ระบบจะแสดงหน้าเว็บในภาพ ๑-34 ซึ่งผู้ใช้จะกดเมนูในช่อง Rule และเลือก ALL-ICMP แล้วหลังจากนั้นให้ทำแบบเดียวกันเพื่อเพิ่มกฎอีกกฎหนึ่งและเลือก SSH จากเมนูในภาพ ๑-34 ในการเลือกแต่ละครั้งผู้ใช้จะเห็นหน้าเว็บหลังเลือกดังภาพ ๑-35 ซึ่งทุกครั้งที่เลือกผู้ใช้ต้องกด Add

สุดท้ายเมื่อเพิ่มกฎเสร็จแล้ว ระบบจะแสดงหน้าสรุปกฎทั้งหมดในกลุ่ม SSH-ICMP ดังภาพ ๑-36

๑.2.5 การเพิ่มกลุ่มกฎรักษาความปลอดภัยให้วีเอ็ม

หลังจากที่มีกลุ่ม SSH-ICMP แล้ว ผู้ใช้สามารถเพิ่มกฎนี้ให้กับวีเอ็ม cirros-1 ได้ โดยผู้ใช้ต้องเลือกแท็บ Compute และแท็บย่อย Instance ระบบจะแสดงเว็บเพจดังภาพ ๑-37 ซึ่งผู้ใช้จะเลือกเมนูถัดจากปุ่ม Create Snapshot แล้วจึงเลือก Edit Security Groups และระบบจะแสดงเว็บเพจในภาพ ๑-38 (บน) ผู้ใช้จะต้องกดปุ่ม “+” ตรงตัวเลือก SSH-ICMP เพื่อเพิ่มกลุ่มของกฎนี้ให้เป็นกฎไฟร์วอลของวีเอ็ม หลังจากนั้นระบบจะแสดงภาพ ๑-38 (ล่าง)

ในภาพ ๑-39 ผู้ใช้จะสามารถ ping และล็อกอินทางไกลด้วย SSH Protocol เครื่องวีเอ็ม cirros-1 จากระบบเครือข่ายภายนอกระบบโอเพนสแตคได้

๑.2.6 การเพิ่ม Template ของเกสต์โอเอสอิมเมจใน Component แกลนซ์

ในอันดับถัดไป ผู้ดูแลระบบจะเพิ่ม Template ของเกสต์โอเอสอิมเมจเข้าสู่ Component แกลนซ์ ของโอเพนสแตค เกสต์โอเอสอิมเมจที่จะเพิ่มในที่นี้คือ เกสต์โอเอส Ubuntu 20.04 เผยแพร่ที่เว็บไซต์ https://cloud-images.ubuntu.com/ โดยที่ผู้ดูแลระบบจะดาวน์โหลด Disk Image ที่ต้องการมาเก็บบไว้ใน Local คอมพิวเตอร์แล้ว upload (Upload) เข้าสู่ระบบโอเพนสแตคโดยใช้ OpenStack Dashboard

$
$ wget https://cloud-images.ubuntu.com/focal/current/focal-server-cloudimg-amd64.img
…
$ ls -l focal-server-cloudimg-amd64.img

หลังจากนั้น ผู้ดูแลระบบจะล็อกอินเข้าเป็นผู้ใช้ Admin และเลือกแท็บ Compute และแท็บย่อย Images ระบบจะแสดงหน้าเว็บเพจแสดงรายการเกสต์โอเอสอิมเมจที่มีอยู่ใน Repository ของ Component แกลนซ์ ดังภาพ ๑-40 ผู้ดูแลระบบจะกดปุ่ม Create Image และระบบจะแสดงหน้าเว็บในภาพ ๑-41 ซึ่งผู้ดูแลระบบจะต้องกรอกข้อมูลดังนี้

  1. Image name : ชื่ออิมเมจในแกลนซ์ ในตัวอย่างนี้คือ ubuntu-focal-server

  2. File : ไฟล์อิมเมจบน Local คอมพิวเตอร์ที่จะ upload ขึ้นสู่แกลนซ์

  3. Format : กำหนดชนิดของอิมเมจ ในตัวอย่างกำหนดให้ใช้ QCOW2 ชนิดของอิมเมจจะต้องตรงกับชนิดของอิมเมจในไฟล์ที่จะ upload จริง

  4. Minimum Disk : กำหนดขนาดของพื้นที่ดิสก์สำหรับเก็บอิมเมจขั้นต่ำที่ต้องมีใน Flavor ที่ใช้รันวีเอ็ม

  5. Minimum Ram : กำหนดขนาดของหน่วยความจำขั้นต่ำที่ต้องมีใน Flavor ที่ใช้รันวีเอ็ม

  6. Visibility : พารามิเตอร์นี้มีทางเลือกสี่แบบได้แก่ 1) public คือกำหนดให้ผู้ใช้ทุกคนสามารถใช้อิมเมจได้ 2) private คือผู้ใช้ทุกคนที่อยู่ใน Project เดียวกันจะเห็นอิมเมจนี้ 3) shared คือผู้ใช้ที่อยู่ในกลุ่มของ Project ที่ผู้ดูแลระบบกำหนดให้ใช้อิมเมจนี้ได้ และ 4) community คือผู้ใช้จะไม่เห็นอิมเมจนี้ตามปกติ แต่จะสามารถใช้งานอิมเมจได้ถ้ารู้ค่า UUID

  7. Protected : ถ้ากำหนดค่าพารามิเตอร์นี้เป็น “Yes” ผู้ใช้จะไม่สามารถลบอิมเมจนี้ออกจากแกลนซ์ได้ (ต้องเป็นผู้ดูแลระบบเท่านั้น)

หลังจากนั้นเมื่อผู้ใช้กดปุ่ม Create Image ระบบจะใช้เวลา upload อิมเมจสักพักและเมื่อเสร็จแล้วจะแสดงหน้าเว็บดังภาพ ๑-42 ในตัวอย่างนี้ ผู้ดูแลระบบได้ upload อิมเมจของเกสต์โอเอสใหม่คือ ubuntu-focal-server ซึ่งผู้ใช้ทุกคนสามารถใช้รันวีเอ็มได้และจะต้องใช้พื้นที่หน่วยเก็บข้อมูลอย่างน้อยขนาด 5 GB และแรมขนาดอย่างน้อย 512 MB ในการรันวีเอ็ม

๑.2.7 การเพิ่ม Flavor

จากข้อมูลเฉพาะของอิมเมจที่เพิ่มเข้าสู่ระบบในตอนก่อน ผู้ใช้จะยังไม่สามารถรันอิมเมจใหม่นี้ได้เพราะว่า Flavor หรือ Spec ของวีเอ็มที่ผู้ดูแลระบบกำหนดค่าไว้ในปัจจุบัน ไม่มี Flavor ใดที่มีค่าขนาดของพื้นที่สำหรับเก็บอิมเมจมากกว่าหรือเท่ากับ 5 GB ตามความต้องการขั้นต่ำในการรันอิมเมจที่เพิ่งกำหนดไปเลย

ด้วยเหตุนี้ ผู้ดูแลระบบจึงจำเป็นต้องเพิ่ม Flavor ใหม่ โดยล็อกอินเข้าเป็นผู้ใช้ Admin และเลือกแท็บ Admin ตามด้วยแท็บย่อย Compute แล้วเลือกแท็บย่อย Flavors ระบบจะแสดงหน้าเว็บเพจแสดงรายการ Flavor ที่มีอยู่ดังภาพ ๑-43 ผู้ดูแลระบบจะกดปุ่ม Create Flavor เพื่อสร้าง Flavor ใหม่ ซึ่งระบบจะแสดงเว็บเพจดังภาพ ๑-44 ซึ่งจะมีปุ่มด้านบนสองปุ่มคือ Flavor Information และ Flavor Access ในส่วนของ Flavor Information ผู้ดูแลระบบจะกรอกข้อมูล Flavor ใหม่ดังนี้ 1) กำหนดค่า Name หรือชื่อ Flavor คือ m1.small.1 และ 2) กำหนดให้ค่า VCPUs คือ 2 คอร์ และ 3) กำหนดให้ขนาดหน่วยความจำสำหรับ Flavor นี้เป็น 1024 MB และ 4) ขนาดของพื้นที่หน่วยเก็บข้อมูลสำหรับเก็บ Disk Image ของเกสต์โอเอสเป็น 8 GB

สำหรับในส่วน Flavor Access ระบบโอเพนสแตคให้ผู้ดูแลระบบเลือกได้ว่าจะให้ผู้ใช้ของ Project ใดใช้ Flavor ใหม่นี้ได้บ้าง ซึ่งถ้าผู้ดูแลระบบไม่เลือก Project ใดจะหมายความว่าผู้ใช้ของทุก Project สามารถใช้ Flavor นี้ได้ หลังจากนั้นระบบจะแสดงรายการ Flavor ชุดใหม่ดังภาพที่ ๑-45

๑.2.8 การรันวีเอ็มโดยใช้เกสต์โอเอสอิมเมจของ Ubuntu

หลังจากที่เตรียมอิมเมจและ Flavor เรียบร้อยแล้ว ผู้ใช้จะรันวีเอ็มโดยล็อกอินเข้าสู่ Project-A ด้วยบัญชีผู้ใช้ A-user และพาสเวิร์ด A-user และเลือกกดแท็บ Compute และ Instance และกดปุ่ม Launch Instance ซึ่งระบบจะแสดงหน้าเว็บในภาพที่ ๑-46 ผู้ใช้ใส่ชื่อวีเอ็มเป็น focal-1 แล้วจึงกดปุ่ม Next เพื่อไปยังหน้าเว็บเพจดังภาพ ๑-47 ที่จะให้ผู้ใช้เลือกว่าจะใช้อิมเมจของเกสต์โอเอสจากแหล่งที่มาใด (Boot Source) ผู้ใช้เลือก Image ซึ่งหมายความว่าจะให้โอเพนสแตคอ่านอิมเมจจาก Repository ของแกลนซ์และทำสำเนาไว้ที่พื้นที่เก็บอิมเมจที่วีเอ็มจะใช้รัน ในช่อง Create New Volume ผู้ใช้เลือก No หมายความว่าผู้ใช้จะให้โอเพนสแตคใช้พื้นที่ในหน่วยเก็บข้อมูล Local ของเครื่อง compute host (Local storage of compute node) ที่โอเพนสแตคเลือกที่จะใช้รันวีเอ็มเป็นที่เก็บอิมเมจของเกสต์โอเอส

หลังจากนั้น ในภาพ ๑-48 ผู้ใช้จะเลือก Flavor m1.small.1 สำหรับวีเอ็ม และกด Next ระบบจะแสดงหน้าเว็บในภาพ ๑-48 ซึ่งระบบจะเลือก Provider1 เป็นระบบเครือข่ายของวีเอ็มเนื่องจากในขณะนี้มีระบบเครือข่ายที่ผู้ใช้ใน Project นี้เลือกใช้ได้อยู่เครือข่ายเดียว หลังจากนั้นเมื่อผู้ใช้กด Next จะเข้าสู่หน้าเว็บให้เลือก Network Ports ซึ่งจะยังไม่ใช้ในตัวอย่างนี้ และผู้ใช้จะกด Next ข้ามไป ในภาพ ๑-50 จะเป็นเว็บเพจให้ผู้ใช้กำหนดค่ากลุ่มของกฎรักษาความปลอดภัยหรือกฎไฟร์วอลสำหรับวีเอ็ม ซึ่งผู้ใช้จะเลือก default และ SSH-ICMP แล้วกด Next ในภาพ ๑-51 ผู้ใช้จะยังไม่ระบุ Key Pair ที่จะใช้สำหรับเข้าถึงวีเอ็ม

ภาพ ๑-52 แสดงเว็บเพจที่ผู้ใช้จะกำหนดค่าพาสเวิร์ดสำหรับล็อกอินเข้าสู่วีเอ็มนี้โดยใช้เครื่องมือ cloud-init ในเว็บเพจนี้ผู้ใช้จะต้องเขียนสคริปต์ในช่อง Customization Script (Modified) ดังนี้

ไฟล์ / ข้อความ
#cloud-config
password: vasabilab
chpasswd: { expire: False }
ssh_pwauth: True

และกดเลือก (เครื่องหมายถูก) ที่กล่อง Configuration Drive

สคริปต์ข้างต้นจะได้รับการรันเมื่อวีเอ็มเริ่มต้นการประมวลผลและจะทำให้ผู้ใช้สามารถล็อกอินเข้าใช้งานวีเอ็มด้วยชื่อล็อกอิน ubuntu และพาสเวิร์ด vasabilab

หลังจากนั้นผู้ใช้กดปุ่ม Launch Instance ระบบจะสร้างวีเอ็มและแสดงเว็บเพจในภาพ ๑-53

ในภาพ ๑-53 ผู้ใช้จะเห็นวีเอ็มใหม่ชื่อ focal-1 ถูกสร้างขึ้นและมีสถานะ Active ผู้ใช้สามารถล็อกอินเข้าใช้วีเอ็มได้สองวิธี วิธีแรกคือการเข้าใช้งานทางคอนโซล (console) อีกวิธีหนึ่งคือการล็อกอินทางไกลด้วย SSH Protocol ในภาพแสดงการเข้าใช้งานด้วยวิธีแรกซึ่งผู้ใช้จะต้องกดปุ่มขยายเมนูถัดจากปุ่ม Create Snapshot และเลือก Console เพื่อเข้าสู่คอนโซลของวีเอ็มดังภาพ ๑-54 ในการใช้งานคอนโซลผู้ใช้ต้องป้อนข้อมูลทางคีย์บอร์ดเท่านั้นและไม่สามารถคัตและเพสต์ (Cut and Paste) ข้อมูลจาก Local คอมพิวเตอร์เข้าสู่คอนโซลเทอร์มินอลได้ ในระบบโอเพนสแตค ก่อนที่จะป้อนข้อมูลทางคอนโซลได้ผู้ใช้ต้องนำเคอร์เซอร์ไปวางและกดเลือกบนแถบสีฟ้าด้านบนของคอนโซลก่อนแล้วจึงเลื่อนเคอร์เซอร์เข้ามาในพื้นที่คอนโซลเพื่อป้อนข้อมูล เบื้องต้นในภาพผู้ใช้จะป้อนชื่อล็อกอิน ubuntu และพาสเวิร์ด vasabilab แล้วจึงล็อกอินเข้าสู่ Command Line เชลล์ของ Ubuntu

อีกวิธีหนึ่งที่จะล็อกอินเข้าสู่วีเอ็มได้คือการล็อกอินทางไกลด้วย SSHProtocol ดังภาพ ๑-55 เนื่องจากวีเอ็ม focal-1 ใช้ระบบเครือข่ายภายนอกที่ระบบโอเพนสแตคใช้บริการโดยตรง ดังนั้นผู้ใช้จึงสามารถอ้างอิงค่าไอพี 192.168.20.165 ได้เลย

๑.2.9 การสร้างคู่คีย์สำหรับล็อกอินเข้าสู่วีเอ็มโดยไม่ต้องใส่พาสเวิร์ด

เพื่อความสะดวกในการสั่งงานวีเอ็ม ผู้ใช้สามารถสร้างคู่คีย์ (Key Pairs) และใช้ในการล็อกอินวีเอ็มได้ ในการสร้างคู่คีย์ ผู้ใช้ต้องเลือกแท็บ Compute และเลือกแท็บย่อย Key Pairs และระบบจะแสดงเว็บเพจในหน้า ๑-56 ซึ่งผู้ใช้สามารถกดปุ่ม Create Key Pair เพื่อสร้างคู่คีย์ หรือกดปุ่ม Import Public Key ในกรณีที่ผู้ใช้มีคู่คีย์อยู่แล้วใน Local คอมพิวเตอร์ และต้องการนำเข้า Public Key เพื่อใช้ในการล็อกอินทางไกล (remote login) หรือสั่งงานวีเอ็มทางไกล (remote execution) หรือกดปุ่ม Delete Key Pair ถ้าผู้ใช้ต้องการลบคู่คีย์ที่มีอยู่ในระบบ

ในการสร้างคู่คีย์ ผู้ใช้กดปุ่ม Create Key Pair ในภาพ ๑-56 แล้วระบบจะแสดงเว็บเพจในภาพ ๑-57 ผู้ใช้จะต้องใส่ชื่อคู่คีย์ซึ่งในตัวอย่างจะเป็น A-user-key และเลือกชนิดของคู่คีย์ในช่อง Key Types ซึ่งผู้ใช้จะต้องเลือกระหว่าง SSH Key และ X.509 certificate ในตัวอย่างนี้เราจะเลือก SSH Key หลังจากนั้นเมื่อกด Create Key Pair ระบบจะแสดงเว็บเพจในภาพ ๑-58 และในขณะเดียวกันระบบจะดาวน์โหลดไฟล์ A-user-key.pem มาที่ directory สำหรับเก็บข้อมูล Download ของเบราว์เซอร์ของผู้ใช้ ไฟล์ A-user-key.pem เป็นไพรเวทคีย์​ (private key) ที่ผู้ใช้สามารถนำไปใช้ได้โดยตรงถ้าผู้ใช้ต้องการล็อกอินเข้าสู่วีเอ็มจาก Local คอมพิวเตอร์ที่เป็นเครื่องลินุกซ์ แต่ถ้าผู้ใช้จะล็อกอินเข้าใช้ด้วยซอฟต์แวร์ putty ผู้ใช้จะต้องทำตามขั้นตอนที่ (https://www.mirantis.com/blog/openstack-security-tip-create-a-keypair-for-accessing-vms/)

๑.2.10 การสร้างวีเอ็มและกำหนดค่าคู่คีย์ให้กับวีเอ็ม

ในการสร้างวีเอ็มที่สามารถใช้คู่คีย์ได้ ผู้ใช้จะสร้างวีเอ็มใหม่ชื่อ focal-2 ซึ่งมีขั้นตอนในการสร้างเหมือนกับเมื่อผู้ใช้สร้างวีเอ็ม focal-1 ในตอนที่ 7.2.1.8 แต่มีขั้นตอนที่แตกต่างคือในขั้นตอนใช้งานคู่คีย์ในภาพ ๑-59 ผู้ใช้จะต้องเลือก A-user-key เป็นคู่คีย์ (หมายเหตุ ผู้ใช้ยังคงต้องกำหนดค่าใน Customization Scripts ในขั้นตอน Configuration ในภาพ ๑-60 เนื่องจากผู้ใช้ยังต้องใช้ป้อนพาสเวิร์ด เมื่อล็อกอินด้วยคอนโซล หลังจากกดปุ่ม Launch Instance ระบบจะแสดงเว็บเพจในภาพ ๑-61)

หลังจากนั้น บน Local คอมพิวเตอร์ ผู้ใช้สามารถใช้คำสั่งข้างล่างเพื่อล็อกอินทางไกลเข้าสู่วีเอ็ม focal-2 โดยไม่ต้องใส่พาสเวิร์ด ดังภาพ ๑-62

On local computer
$ ssh  -i  ./A-user-key.pem  ubuntu@192.168.20.162
…
focal-2 $

แต่อย่างไรก็ตาม ถ้าผู้ใช้จะเข้าใช้งานวีเอ็มทางคอนโซล (ดังภาพ ๑-63) ผู้ใช้จะต้องใช้พาสเวิร์ด ตามค่าที่กำหนดในภาพ ๑-60

๑.2.11 การลบวีเอ็ม

เพื่อให้ง่ายต่อการอธิบายในลำดับถัดไป การลบวีเอ็มที่ผู้ใช้ไม่ได้ใช้ เราจะลบวีเอ็ม cirros-1 และ focal-1 ออกจากระบบโอเพนสแตค ในภาพ ๑-61 ผู้ใช้จะต้องเช็คกล่องสี่เหลี่ยมที่อยู่หน้าชื่อ cirros-1 และ focal-1 หลังจากนั้นกดปุ่ม Delete Instances

๑.2.12 การสร้างระบบเครือข่ายเสมือนภายใน Project

ในกรณีที่ผู้ใช้ต้องการสร้างระบบเครือข่ายภายในเพื่อให้วีเอ็มจำนวนหนึ่งสื่อสารกันผ่านระบบเครือข่ายนี้ และอนุญาตให้วีเอ็มเหล่านั้นสื่อสารกับคอมพิวเตอร์ภายนอกเครือข่ายภายในนี้ได้ด้วย ผู้ใช้จะต้องสร้างระบบเครือข่ายเสมือนภายในและสร้างเร้าเตอร์เสมือนสำหรับระบบเครือข่ายนั้น ในตอนนี้ จะบรรยายขั้นตอนในการสร้างระบบเครือข่ายเสมือน เร้าเตอร์เสมือน และวีเอ็มบนระบบเครือข่ายเสมือนนั้น

เบื้องต้น ผู้ใช้สามารถดู Topology ของระบบเครือข่ายได้โดยเลือกแท็บ Network และเลือกแท็บย่อย Network Topology ระบบจะแสดงเพจดังภาพ ๑-64 ซึ่งแสดงว่ามีระบบเครือข่ายภายนอกที่โอเพนสแตคเชื่อมต่อด้วยเพื่อสื่อสารกับโลกภายนอกชื่อ provider1 และมีค่าซับเน็ตคือ 192.168.20.0/24 เครือข่ายนี้ถูกสร้างขึ้นเมื่อผู้ติดตั้งโอเพนสแตคใช้สคริปต์ exe-stage36-USER-initial-network.sh (สามารถดูรายละเอียดคำสั่งได้บน github) นอกจากแสดงภาพระบบเครือข่ายแล้วหน้าเว็บเพจ Network Topology ยังแสดงว่ามีวีเอ็ม (focal-2) เชื่อมต่อกับระบบเครือข่ายนี้ด้วย

ในการสร้างระบบเครือข่ายเสมือนภายในใหม่ ผู้ใช้ต้องกดแท็บ Network และแท็บย่อย Networks ระบบจะแสดงเว็บเพจดังภาพ ๑-65 หลังจากนั้น ผู้ใช้จะต้องกดปุ่ม Create Network ระบบจะแสดงเว็บเพจดังภาพ ๑-66 ซึ่งผู้ใช้จะกำหนดชื่อระบบเครือข่ายนี้คือ A-net-1 ในเว็บเพจนี้ระบบจะเลือกช่อง Enable Admin State และ Create Subnet เป็นค่าดีฟอลต์ เมื่อผู้ใช้กดปุ่ม Next ระบบจะแสดงเว็บเพจในภาพ ๑-67 ซึ่งผู้ใช้จะกำหนดชื่อซับเน็ตของระบบเครือข่ายนี้คือ A-net-1-subnet และให้ซับเน็ตมีค่า Network Address เป็น 10.50.11.0/24 ระบบโอเพนสแตคจะกำหนดให้ค่าดีฟอลต์ของไอพีของเกตเวย์ (gateway) ของระบบเครือข่ายเสมือนนี้เป็น 10.50.11.1 ถ้าต้องการให้เป็นค่าไอพีอื่นในซับเน็ตก็สามารถระบุค่าในช่อง Gateway IP ได้ (ถ้าไม่ระบุระบบจะใช้ค่าดีฟอลต์) ในกรณีที่ผู้ใช้ไม่ต้องการให้ระบบเครือข่ายเสมือนมีเกตเวย์ ผู้ใช้ต้องใส่เครื่องหมายถูกหน้ากล่องในช่อง Disable Gateway เมื่อเสร็จแล้วให้กด Next ​

ระบบจะแสดงหน้าเว็บเพจในภาพ ๑-68 เพื่อให้ผู้ใช้กำหนดรายละเอียดของซับเน็ต ซึ่งระบบจะเลือกให้ระบบเครือข่ายเสมือนนี้ใช้ DHCP Protocol เป็นค่าดีฟอลต์ ถ้าผู้ใช้ไม่ต้องการใช้ DHCP ก็ต้องยกเลิกการเช็คค่าในกล่อง Enable DHCP ในกล่องถัดไป ระบบจะให้ผู้ใช้กำหนดค่า Allocation Pool ว่าผู้ใช้ต้องการให้ระบบแจกค่าไอพีในช่วงค่าไหนให้แก่วีเอ็ม ถ้าไม่ระบุโอเพนสแตคจะแจกค่าไอพีจากค่าไอพีที่ใช้ได้ในซับเน็ต ในช่อง DNS Name Servers ผู้ใช้สามารถกำหนดรายการของ DNS servers ที่ผู้ใช้จะใช้ ในตัวอย่างนี้เราใช้ 8.8.8.8 สำหรับช่อง Host Routes นั้นเราจะไม่กล่าวถึงในตัวอย่างนี้ เมื่อเสร็จแล้ว ผู้ใช้จะกดปุ่ม Create และระบบจะแสดงเว็บเพจในภาพ ๑-69 และเมื่อผู้ใช้กดดูภาพ Topology ของระบบเครือข่ายใน Project ระบบจะแสดงภาพ Topology ในภาพ ๑-70

๑.2.13 การสร้างเร้าเตอร์สำหรับเชื่อมต่อระบบเครือข่ายเสมือน

จาก Topology ในภาพ ๑-70 ผู้ใช้จะเห็นว่าระบบเครือข่ายเสมือนที่สร้างขึ้นยังไม่ได้รับการเชื่อมต่อกับระบบเครือข่ายภายนอกด้วยเร้าเตอร์ ดังนั้นถ้าเชื่อมต่อวีเอ็มเข้ากับระบบเครือข่ายนี้ วีเอ็มภายในระบบเครือข่ายเสมือนจะสามารถสื่อสารกันได้ แต่จะไม่สามารถสื่อสารกับคอมพิวเตอร์ที่อยู่ภายนอกระบบเครือข่ายได้

ในการสร้างเร้าเตอร์ ผู้ใช้จะต้องเลือกแท็บ Network และเลือกแท็บย่อย Routers ระบบจะแสดงเว็บเพจดังภาพ ๑-71 ผู้ใช้ต้องกดปุ่ม Create Router เพื่อสร้างเร้าเตอร์เสมือนซึ่งระบบจะแสดงเว็บเพจในภาพ ๑-72 ซึ่งผู้ใช้กำหนดชื่อเร้าเตอร์คือ A-router-1 และเลือก Provider1 ในช่อง External Network เพื่อกำหนดให้ระบบเครือข่าย Provider1 เป็นระบบเครือข่ายภายนอกของเร้าเตอร์นี้ หลังจากนั้น ผู้ใช้จะกดปุ่ม Create Router และระบบจะแสดงเว็บเพจในหน้า ๑-73 แสดงรายการของเร้าเตอร์ใน Project

เมื่อผู้ใช้เรียกดูภาพ Topology ของระบบเครือข่ายในภาพ ๑-74 จะเห็นว่ามีเร้าเตอร์เสมือนถูกสร้างขึ้นและเชื่อมต่อเข้ากับระบบเครือข่ายภายนอก แต่ยังไม่ได้เชื่อมต่อกับระบบเครือข่ายเสมือนภายใน ดังนั้น ในอันดับถัดไป ผู้ใช้จะต้องเลือกแท็บ Network แท็บย่อย Routers ซึ่งระบบจะแสดงเว็บเพจดังภาพ ๑-73 และผู้ใช้จะต้องกดบนชื่อ “A-router-1” หลังจากนั้น ระบบจะแสดงหน้าเว็บเพจในภาพ ๑-75 ซึ่งจะแสดงรายละเอียดของเร้าเตอร์

ในการเชื่อมต่อเร้าเตอร์เข้ากับระบบเครือข่ายเสมือนภายใน ผู้ใช้ต้องกดแท็บ Interface ในภาพ ๑-75 และระบบจะแสดงเว็บเพจในหน้า ๑-76 ผู้ใช้ต้องกดปุ่ม Add Interface และระบบจะแสดงเว็บเพจในภาพ ๑-77 ซึ่งผู้ใช้จะเลือกซับเน็ตที่จะเชื่อมต่อกับเร้าเตอร์ A-router-1 ในช่อง Subnet ในภาพ ๑-77 ผู้ใช้เลือก A-net-1-subnet แล้วกดปุ่ม submit หลังจากนั้น ระบบจะแสดงเว็บเพจในภาพ ๑-78 เพื่อแสดงว่าการเชื่อมต่อเสร็จเรียบร้อยแล้ว เมื่อผู้ใช้เรียกดู Topology ของระบบเครือข่าย ระบบจะแสดงภาพดังภาพ ๑-79

๑.2.14 การสร้างวีเอ็มเชื่อมต่อระบบเครือข่ายเสมือน

ในอันดับถัดไป ผู้ใช้จะสร้างวีเอ็มที่มีเกสต์โอเอสเป็น Ubuntu เหมือนกับที่เคยสร้างก่อนหน้าแต่จะเชื่อมต่อวีเอ็มเข้ากับระบบเครือข่ายเสมือนภายใน A-net-1 แทนที่จะเชื่อมต่อกับระบบเครือข่าย Provider1 โดยที่ผู้ใช้จะตั้งชื่อวีเอ็มใหม่นี้ว่า focal-3 ซึ่งในการสร้างวีเอ็มนี้ ผู้ใช้จะทำขั้นตอนทุกอย่างเหมือนกับที่ได้บรรยายในตอน 7.2.1.10 แต่เปลี่ยนการเลือกระบบเครือข่ายเป็นดังภาพ ๑-80 แทน

หลังจากนั้น ระบบจะแสดงเว็บเพจในภาพ ๑-81 ซึ่งจะเห็นได้ว่าวีเอ็ม focal-3 ได้รับกำหนดค่า Fixed IP (Fixed IP) เป็น 10.50.11.163 ซึ่งเป็นค่าไอพีภายในซับเน็ต A-net-1-subnet เมื่อเรียกดูภาพ Topology จะได้ Topology ดังภาพ ๑-82 ซึ่งจะเห็นว่า focal-3 นั้นอยู่ภายในระบบเครือข่าย A-net-1 ผู้ใช้สามารถใช้คอนโซลล็อกอินเข้าสู่ focal-3 ได้ดังภาพ ๑-83 และจะเห็นว่าผู้ใช้สามารถสื่อสารกับอินเทอร์เน็ตได้ (ping www.google.com ได้) ทั้งนี้เป็นเพราะข้อความจากวีเอ็มจะถูกส่งผ่านเร้าเตอร์เสมือนและผ่านกระบวนการ SNAT และข้อความจะถูกส่งต่อออกสู่ระบบเครือข่ายภายนอก Provider1 และถูกส่งต่อออกสู่อินเทอร์เน็ตในที่สุด

อย่างไรก็ตาม ผู้ใช้จะไม่สามารถสื่อสารกับวีเอ็ม focal-3 จากระบบเครือข่ายภายนอกได้ ดังภาพที่ ๑-84 ซึ่งผู้ใช้พยายาม ping เครื่อง focal-3 จาก Local คอมพิวเตอร์ที่เชื่อมต่อกับระบบเครือข่าย Provider1

๑.2.15 การจัดสรร Floating IP ให้วีเอ็ม

Floating IP (Floating IP) คือค่าไอพีของระบบเครือข่ายภายนอกที่โอเพนสแตคอนุญาตให้ผู้ใช้นำไปสร้างความเกี่ยวข้อง (associate) เข้ากับ Fixed IP (Fixed IP) ของวีเอ็มที่เชื่อมต่อกับระบบเครือข่ายเสมือนภายใน (เช่น A-net-1 เป็นต้น) ที่มีเร้าเตอร์เชื่อมต่อกับระบบเครือข่ายภายนอกที่มีค่าซับเน็ตเป็นของ Floating IP นั้น ยกตัวอย่างเช่น ไอพีในซับเน็ต 192.168.20.0/24 ของระบบเครือข่ายภายนอก Provider1 สามารถถูกนำไปใช้เป็น Floating IP ของวีเอ็มที่เชื่อมต่อกับระบบเครือข่ายภายใน A-net-1 เนื่องจากทั้งสองระบบเครือข่ายมีเร้าเตอร์เชื่อมต่อกัน สำหรับที่มาของ Floating IP ของแต่ละ Project นั้น ผู้ดูแลระบบจะเป็นผู้กำหนด quota ว่าแต่ละ Project จะสามารถใช้ไอพีได้กี่ไอพี

เมื่อต้องการใช้ Floating IP ผู้ใช้จะต้องขอจัดสรร (allocate) จากพูล (pool) ของระบบ โดยเลือกกดแท็บ Network และแท็บย่อย Floating IPs ระบบจะแสดงเว็บเพจดังภาพ ๑-85 หลังจากนั้นผู้ใช้จะต้องกดปุ่ม Allocate IP to Project ซึ่งระบบจะแสดงเว็บเพจในภาพ ๑-86

ผู้ใช้จะต้องเลือกในช่อง Pool ว่าจะจัดสรร Floating IP จากระบบเครือข่ายภายนอกใด ซึ่งในที่นี้มีอยู่เครือข่ายเดียวคือ provider1 ขอให้สังเกตว่า quota ของ Floating IP ของ Project Project-A คือ 8 ไอพี ท้ายที่สุด ผู้ใช้จะกดปุ่ม Allocate IP ซึ่งระบบจะจัดสรรไอพีให้และแสดงรายการไอพีในเว็บเพจในภาพ ๑-87 ในเว็บเพจนั้น ผู้ใช้จะต้องเลือกค่า Floating IP ที่ต้องการและกดปุ่ม Associate ในบรรทัดเดียวกันกับค่าไอพีนั้น ระบบจะแสดงเว็บเพจในภาพ ๑-88

ในอันดับถัดไป ผู้ใช้จะต้องเลือกว่าจะให้ไอพี 192.168.20.196 มีความเกี่ยวข้องกับ Fixed IP ใด ซึ่ง Component นิวตรอนของโอเพนสแตคกำหนดให้ทุกการเชื่อมต่อระหว่างวีเอ็มกับระบบเครือข่ายเป็น network port ผู้ใช้จะต้องเลือกจากลิสต์ของ Fixed IP ในเมนูว่าจะสร้างความเกี่ยวข้องกับไอพีใด ซึ่งในภาพจะได้เป็นค่าไอพี 10.50.11.163 ของวีเอ็ม focal-3 ถัดจากนั้น ผู้ใช้กด Associate แล้วระบบจะแสดงเว็บเพจสรุปในภาพ ๑-89 หลังจากนั้น เมื่อผู้ใช้เลือกแท็บ Compute และแท็บย่อย Instances ระบบจะแสดงข้อมูลเกี่ยวกับ Floating IP เพิ่มเติมในรายการของวีเอ็มในบรรทัดที่แสดงข้อมูลของ focal-3 ดังภาพ ๑-90

ในภาพ ๑-91 ผู้ใช้สามารถล็อกอินทางไกลจาก Local คอมพิวเตอร์ของผู้ใช้เข้าสู่วีเอ็ม focal-3 โดยใช้ ssh protocol ผ่าน Floating IP เมื่อล็อกอินแล้วจะเห็นว่าเกสต์โอเอสกำหนดให้ Fixed IP เป็นไอพีของเน็ตเวิร์คอินเตอร์เฟสของวีเอ็ม Floating IP เป็นไอพีที่ระบบโอเพนสแตคทำ NAT ให้กับวีเอ็มเท่านั้น

Suspend Instance คือการหยุดการประมวลผลของวีเอ็มและเขียนข้อมูลในหน่วยความจำลงสู่หน่วยเก็บข้อมูลหลังจากนั้นข้อมูลในหน่วยความจำจะถูกลบไป ผู้ใช้สามารถสั่งให้วีเอ็มกลับมาประมวลผลคำสั่งต่อจากคำสั่งสุดท้ายก่อนการ Suspend ด้วยคำสั่ง Resume Instance ซึ่งไฮเปอร์ไวเซอร์จะอ่านข้อมูลหน่วยความจำของวีเอ็มจากหน่วยเก็บข้อมูลกลับสู่หน่วยความจำก่อนสั่งให้วีเอ็มประมวลผลต่อไป (https://wiki.openstack.org/wiki/Kvm-Pause-Suspend)

  3. Shelve Instance คือการ shutdown เกสต์โอเอสของวีเอ็มและทำ Snapshot (snapshot) ของ Disk Image และ Volume ของวีเอ็ม หลังจากทำ Snapshot แล้วข้อมูลในหน่วยเก็บข้อมูลที่วีเอ็มใช้ตอนรันอยู่อาจถูกลบทิ้ง หรือ คงไว้ที่เดิม หรือลบทิ้งหลังจากระยะเวลาหนึ่งขึ้นอยู่กับการกำหนดค่าใน Component โนวา ผู้ใช้สามารถใช้คำสั่ง Unshelve Instance เพื่อนำข้อมูลจาก Snapshot ที่เก็บไว้กลับมาใช้ และบูทวีเอ็มใหม่จากข้อมูลนั้น

(https://docs.openstack.org/mitaka/user-guide/cli_stop_and_start_an_instance.html)

  1. Shut off Instance คือการ shutdown เกสต์โอเอสของวีเอ็มและจะคงเกสต์โอเอสอิมเมจใว้ในหน่วยเก็บข้อมูลที่วีเอ็มใช้แต่เดิม และ (ถ้ามี) จะลบ Volume ชั่วคราว (ephemeral volume) ออก ผู้ใช้สามารถใช้คำสั่ง Start Instance เพื่อบูทวีเอ็มจากอิมเมจในหน่วยเก็บข้อมูลเดิมของวีเอ็มได้ (https://www.quora.com/What-is-the-difference-between-shelving-an-instance-and-shutting-down-in-openstack)

ในภาพ ๑-92 ผู้ใช้จะเลือก Shut Off Instance แล้วหลังจากนั้นระบบจะแสดงเว็บเพจดังภาพ ๑-93

๑.2.17 การรันวีเอ็มบนหน่วยเก็บข้อมูล Volume

การรันวีเอ็มบน Volume Storage เป็นการสั่งให้ Component โนวา เก็บข้อมูลอิมเมจของเกสต์โอเอสไว้ที่หน่วยเก็บข้อมูล Volume (Volume Storage) ของ Component ซินเดอร์ แล้วจึงรันวีเอ็ม ซึ่งแตกต่างจากแบบที่ไม่ใช้หน่วยเก็บข้อมูล Volume ซึ่งจะเก็บอิมเมจของเกสต์โอเอสไว้บนหน่วยเก็บข้อมูล Local ของเครื่องที่โนวารันวีเอ็ม

การรันวีเอ็มบน Volume มีข้อดีดังนี้

  1. ผู้ใช้สามารถเลือกที่จะไม่ลบ Volume ที่เก็บเกสต์โอเอสอิมเมจหลังจาก Destroy วีเอ็มแล้ว ทำให้ข้อมูลที่เก็บอยู่ในเกสต์โอเอสอิมเมจไม่สูญหาย ผู้ใช้อาจนำ Volume นั้นกลับมารันวีเอ็มอีกครั้งหนึ่ง หรือนำไปเป็น Volume ข้อมูลให้กับวีเอ็มอื่นก็ได้

  2. ผู้ใช้สามารถใช้ Component ซินเดอร์แบ็คอัพ (cinder backup) เพื่อใช้แบ็คอัพข้อมูลของวีเอ็มในหน่วยเก็บข้อมูลแบบออบเจ็กต์ เช่น Component สวิฟต์ (https://github.com/openstack/swift) ของโอเพนสแตค เป็นต้น

ในการรันวีเอ็มแบบใช้ Volume ผู้ใช้จะเริ่มต้นรันวีเอ็มเหมือนที่บรรยายในตอนที่ 7.2.1.14 แต่ในครั้งนี้ผู้ใช้จะให้ชื่อวีเอ็มว่า focal-vol ดังภาพ ๑-94 หลังจากนั้น ในภาพ ๑-95 เมื่อผู้ใช้ระบุค่าที่มาของเกสต์โอเอสอิมเมจ ผู้ใช้จะกำหนดค่าในช่อง Select Boot Source ให้เป็น Image ซึ่งหมายความว่าผู้ใช้จะอ้างอิงข้อมูล Disk Image ของวีเอ็มจาก image template ใน Repository ของ Component แกลนซ์ของโอเพนสแตค

ในภาพ ๑-95 ผู้ใช้ต้องเลือก Yes ในช่อง Create New Volume เพื่อให้ Component โนวาของโอเพนสแตค ใช้หน่วยเก็บข้อมูล Volume เพื่อเก็บอิมเมจของเกสต์โอเอส ในช่อง Volume Size ผู้ใช้ต้องระบุขนาดของ Volume ด้วย ซึ่งในตัวอย่างนี้กำหนดให้เป็น 10 GB และสุดท้าย ผู้ใช้จะเลือก No ในช่อง Delete Volume on Instance Delete เพื่อที่จะเก็บหน่วยเก็บข้อมูล Volume ของวีเอ็มนี้ไว้ถาวร ไม่ลบทิ้งเมื่อผู้ใช้ลบวีเอ็ม ถัดจากนั้นผู้ใช้จะเลือก ubuntu-focal-server เป็นเกสต์โอเอสอิมเมจ ในภาพ ๑-95 และที่เหลือจะทำเหมือนตอน 7.2.1.14 และระบบจะแสดงเว็บเพจดังภาพ ๑-96 หลังจากกดปุ่ม Launch Instance

หลังจากที่ผู้ใช้รันวีเอ็มแล้ว ผู้ใช้สามารถดูรายละเอียดของ Volume ที่วีเอ็มใช้ได้ โดยเลือกแท็บ Volumes และแท็บย่อย Volumes ระบบจะแสดงรายการ Volume ดังภาพ ๑-97 ซึ่งจะเห็นว่ามี Volume ขนาด 10 GB ถูกสร้างขึ้นและถูกกำหนดให้เป็นอุปกรณ์ /dev/vda บนเครื่อง focal-vol

ถัดจากนั้น ผู้ใช้จะสร้าง Floating IP 192.168.20.176 ดังภาพ ๑-98 และนำไอพีนั้นไปสร้างความเกี่ยวข้องกับ Fixed IP 10.50.11.220 ดังภาพที่ ๑-99

หลังจากนั้น ผู้ใช้จะล็อกอินทางไกลจาก Local คอมพิวเตอร์เข้าสู่เครื่องวีเอ็ม focal-vol ดังภาพ ๑-100 และเมื่อใช้คำสั่ง df -h ดังภาพ ๑-101 จะเห็นว่า directory รูท (root) “/” ของไฟล์ซิสเต็มของวีเอ็มนั้นอยู่ใน partition /dev/vda1 ของอุปกรณ์ /dev/vda

๑.2.18 การสร้าง Volume ข้อมูลและเชื่อมต่อ Volume ข้อมูลเข้ากับวีเอ็มแบบ Hot Plug

ในการใช้งานวีเอ็ม ผู้ใช้อาจต้องการสร้างเพิ่มอุปกรณ์เก็บข้อมูลเนื่องจากมีความต้องการที่จะเก็บข้อมูลมากขึ้นกว่าขนาดของอุปกรณ์ที่มีอยู่ ระบบโอเพนสแตคอนุญาตให้ผู้ใช้สร้างหน่วยเก็บข้อมูล Volume เพิ่มได้และผู้ใช้สามารถเชื่อมต่ออุปกรณ์ใหม่ได้ในขณะที่เครื่องวีเอ็มรันโดยไม่จำเป็นต้องปิดเครื่อง (shut off) หรือรีบูท (reboot) เครื่องใหม่ เราเรียกความสามารถเช่นนี้ว่า Hot Plug

ในการสร้าง Volume ผู้ใช้ต้องเลือกแท็บ Volumes และแท็บย่อย Volumes และระบบจะแสดงเว็บเพจดังภาพ ๑-97 ผู้ใช้ต้องกดปุ่ม Create Volume ระบบจะแสดงเว็บเพจดังภาพ ๑-102 ในภาพ ผู้ใช้ใส่ชื่อ Volume Name เป็น data1 และกำหนดขนาดของหน่วยเก็บข้อมูล Volume เท่ากับ 1 GB ผู้ใช้จะสังเกตว่าระบบจะแสดงข้อมูล quota ในด้านขวาของเว็บเพจ และสุดท้ายผู้ใช้กดปุ่ม Create Volume

หลังจากนั้นระบบจะแสดงเว็บเพจแสดงรายการ Volume ที่มีอยู่ใน Project ในภาพ ๑-103 ซึ่งผู้ใช้จะกดปุ่มขยายเมนูที่อยู่ถัดจากปุ่ม Edit Volume ในบรรทัดเดียวแสดงข้อมูลของ Volume data1 เมื่อเมนูขยายดังภาพแล้วให้เลือก Manage Attachments และระบบจะแสดงเว็บเพจดังภาพ ๑-104 ในเว็บเพจนั้น ผู้ใช้จะเลือกวีเอ็มที่จะนำ Volume ไปเชื่อมต่อแบบ Hot Plug ในช่อง Attach to Instance คือ focal-vol แล้วกดปุ่ม Attach Volume และระบบจะแสดงเว็บเพจในภาพ ๑-105 ในที่สุด ขอให้สังเกตว่าสถานะของ Volume เปลี่ยนจาก Available เป็น in-use

ในการใช้งาน Volume ในเกสต์โอเอส ผู้ใช้จะต้องล็อกอินเข้าสู่วีเอ็ม focal-vol แล้วใช้คำสั่ง lsblk ของลินุกซ์แสดงรายการอุปกรณ์หน่วยเก็บข้อมูลแบบบล็อก ( Block Storage ) ในเกสต์โอเอส ผู้ใช้จะเห็นว่ามีอุปกรณ์ดิสก์ชื่อ vdb เพิ่มขึ้นมาในระบบดังภาพ ๑-106

ในอันดับถัดไปผู้ใช้จะต้องใช้คำสั่ง fdisk ดังภาพ ๑-107 เพื่อสร้างดิสก์พาร์ทิชั่น (disk partition) /dev/vdb1 ซึ่งผู้ใช้จะป้อนข้อมูล “n” หมายถึงจะสร้างพาร์ทิชั่นใหม่บนอุปกรณ์ /dev/vdb และกด “p” เมื่อซอฟต์แวร์ให้เลือกระหว่าง p และ e และในตัวอย่างนี้ เมื่อซอฟต์แวร์ให้กำหนดค่า partition number และ first sector และ last sector ให้ผู้ใช้กด enter คือใช้ค่าดีฟอลต์ สุดท้ายให้ผู้ใช้กด “w” ดังภาพเพื่อบันทึกข้อกำหนดในอุปกรณ์

เมื่อผู้ใช้ใช้คำสั่ง lsblk และ lsblk -f บน Command Line เกสต์โอเอสจะแสดงหน้าจอที่มีข้อมูลของดิสก์พาร์ทิชั่น /dev/vdb1 ดังภาพ ๑-108 ถัดจากนั้น ในภาพ ๑-109 ผู้ใช้จะใช้คำสั่ง mkfs.ext4 เพื่อฟอร์แมต (format) ดิสก์พาร์ทิชั่น /dev/vdb1 ให้ใช้ ext4 ฟอร์แมท และใช้คำสั่ง lsblk -f เพื่อรายงานสถานะดิสก์ฟอร์แมต

สุดท้ายในภาพ ๑-110 ผู้ใช้จะสร้าง directory /data1 ในไฟล์ซิสเต็ม และใช้คำสั่ง mount เพื่อทำให้พาร์ทิชั่น /dev/vdb1 กลายเป็นส่วนหนึ่งของไฟล์ซิสเต็มที่สามารถเข้าถึงได้ทาง /data1

๑.2.19 การสร้างระบบเครือข่ายเสมือนใหม่และเชื่อมต่อเข้ากับวีเอ็มแบบ Hot Plug

หลังจากที่ใช้งานวีเอ็มไปสักพัก ผู้ใช้อาจต้องการเพิ่มระบบเครือข่ายเสมือนและเชื่อมต่อระบบเครือข่ายนั้นเข้ากับวีเอ็มแบบ Hot Plug (hot plug) คือไม่ต้องปิดหรือรีบูทวีเอ็มเพื่อที่จะใช้งานระบบเครือข่ายนั้น

ในอันดับแรก ผู้ใช้ต้องสร้างระบบเครือข่ายภายในดังกล่าวก่อน โดยกดแท็บ Network และแท็บย่อย Networks เหมือนที่ได้บรรยายในตอน 7.2.1.14 แล้วกดปุ่ม Create Network ระบบจะแสดงเว็บเพจดังภาพ ๑-111 ซึ่งผู้ใช้จะตั้งชื่อระบบเครือข่ายเสมือนใหม่นี้ว่า internal1 และกดปุ่ม Next

ระบบจะแสดงเว็บเพจดังภาพ ๑-112 ซึ่งผู้ใช้จะกำหนดค่า Subnet Name เป็น internal1-subnet และกำหนดค่า Network Address ให้เป็น 192.168.200.0/24 และเนื่องจากผู้ใช้จะใช้ระบบเครือข่ายนี้เพื่อการเชื่อมต่อภายในระหว่างวีเอ็มเท่านั้น ดังนั้นผู้ใช้จะไม่ใช้ระบบเครือข่ายนี้เชื่อมต่อกับเร้าเตอร์และจะเลือกเช็คถูกตรงกล่อง Disable Gateway ในภาพนี้ ถัดจากนั้นเมื่อผู้ใช้กดปุ่ม Next

ระบบจะแสดงเว็บเพจดังภาพ ๑-113 ซึ่งผู้ใช้จะยกเลิกการเช็คเครื่องหมายถูกในกล่อง Enable DHCP เนื่องจากผู้ใช้จะกำหนดค่าไอพีแอดเดรสในเกสต์โอเอสด้วยตนเอง (หมายเหตุ ถึงแม้ว่าผู้ใช้จะไม่ใช้ DHCP ระบบโอเพนสแตคยังคงกำหนดค่าไอพีสำหรับการเชื่อมต่อระหว่างวีเอ็มกับระบบเครือข่ายนี้ให้ เพียงแต่จะไม่ใช้ DHCP protocol เข้าไปกำหนดค่าไอพีในเกสต์โอเอสให้เท่านั้น สุดท้ายเมื่อกดปุ่ม Create ระบบเครือข่ายเสมือน internal1 จะถูกสร้างขึ้น และโอเพนสแตคจะแสดงรายการระบบเครือข่ายเสมือนดังภาพ ๑-114)

ในอันดับถัดไป ผู้ใช้จะเลือกแท็บ Compute และแท็บย่อย Instance และระบบจะแสดงรายการวีเอ็มดังภาพ ๑-115 ผู้ใช้จะขยายเมนูถัดจากปุ่ม Create Snapshot และเลือก Attach Interface ซึ่งระบบจะแสดงเว็บเพจดังภาพ ๑-116 ที่ผู้ใช้จะกำหนดค่าระบบเครือข่าย internal1 ในช่อง Network แล้วกดปุ่ม Attach Interface

ผู้ใช้สามารถตรวจสอบสถานการณ์เชื่อมต่อได้โดยเรียกดูภาพ Topology ของระบบเครือข่ายและวีเอ็มใน Project ระบบจะแสดงภาพ Topology ดังภาพ ๑-117 นอกจากนั้น เมื่อผู้ใช้เลือกกดแท็บ Compute และแท็บย่อย Instances ระบบจะแสดงรายการวีเอ็มดังภาพ ๑-118 ซึ่งจะเห็นว่ามีข้อมูลไอพีของระบบเครือข่าย internal1 ปรากฏขึ้นที่บรรทัดข้อมูลของวีเอ็ม focal-vol

เพื่อให้เกสต์โอเอสสามารถใช้งานระบบเครือข่าย internal1 ได้ ผู้ใช้จะล็อกอินเข้าสู่เครื่อง focal-vol และออกคำสั่งบน Command Line ดังภาพที่ ๑-119 ในภาพ ผู้ใช้จะใช้คำสั่งต่อไปนี้

  1. คำสั่ง “ip link” จะแสดงรายละเอียดของเน็ตเวิร์คอินเตอร์เฟสที่มีอยู่ในระบบ ซึ่งจะเห็นว่ามีนิค (NIC) ens8 เป็นนิคใหม่ที่เพิ่งเชื่อมต่อเข้ามา

  2. คำสั่ง “sudo ip link set dev ens8 up” จะเปลื่ยนสถานะของนิค ens8 เป็น UP คือพร้อมให้บริการ

  3. คำสั่ง “sudo ip addr add 192.168.200.172/24 dev ens8” จะกำหนดค่าไอพีของ ens8 ให้เป็น 192.168.200.172 (หมายเหตุ ผู้ใช้จะต้องกำหนดค่าไอพีในเน็ตเวิร์คสแตคของเกสต์โอเอสให้ตรงกับที่โอเพนสแตคกำหนดให้ เนื่องจากค่าไอพีและแมคแอดเดรสของนิคจะถูกนำไปใช้ในการจัดการเน็ตเวิร์คของ Component นิวตรอน)

หลังจากรันคำสั่งข้างต้นแล้วผู้ใช้สามารถใช้คำสั่ง “ip addr” เพื่อรายงานสถานะของนิคของเกสต์โอเอสดังภาพ ๑-120

เพื่อทดสอบว่าระบบเครือข่าย internal1 ใช้งานได้ ผู้ใช้จะใช้วิธีเดียวกันกับที่ศึกษามาในตอนนี้ เชื่อมต่อแบบ Hot Plug ระบบเครือข่าย internal1 เข้ากับวีเอ็ม focal-2 ซึ่งหลังจากเชื่อมต่อแล้ว Component นิวตรอนของโอเพนสแตคจะกำหนดให้ network port ที่ internal1 เชื่อมต่อกับ focal-2 มีค่าไอพีเป็น 192.168.200.24 ดังภาพ ๑-121 ภาพที่ ๑-122 แสดง Topology ที่แสดงการเชื่อมต่อระหว่าง focal-vol และ focal-2 ด้วยระบบเครือข่ายเสมือน internal1

ก่อนที่จะสามารถใช้งานระบบเครือข่ายได้ ผู้ใช้ต้องล็อกอินเข้าสู่วีเอ็ม focal-2 ดังภาพ ๑-123 และกำหนดค่าไอพีให้นิค ens7 ให้เป็น 192.168.200.24 และเปลี่ยนสถานะให้เป็น UP ดังภาพ ๑-124 แล้วหลังจากนั้น ผู้ใช้จะสามารถ ping ไอพี 192.168.200.172 ได้ ดังภาพ ๑-125

๑.2.20 การปรับเปลี่ยน quota ของ Project

ถึงจุดนี้ ถ้าผู้ใช้เข้าเช็คที่ Overview ของ Project Project-A ดังภาพ ๑-126 ผู้ใช้จะเห็นว่า จำนวน network port ใน Project นั้นใช้หมดแล้ว ซึ่งจะส่งผลให้ผู้ใช้ไม่สามารถใช้ระบบเครือข่ายได้อีก ซึ่งจะส่งผลกระทบให้ผู้ใช้ไม่สามารถสร้างวีเอ็มเพิ่มได้ด้วย (ถึงแม้ว่าจะมี quota อื่นเพียงพอก็ตาม) หากผู้ใช้ต้องการขยาย quota ผู้ใช้จะต้องแจ้งผู้ดูแลระบบให้ปรับ quota ให้

หลังจากได้รับคำร้องขอแล้ว ผู้ดูแลระบบจะเลือกแท็บ identity และเลือกแท็บย่อย Projects ระบบจะแสดงเว็บเพจดังภาพ ๑-127 ผู้ใช้จะขยายเมนูถัดจากปุ่ม Manage Members และขยายเมนู แล้วเลือก Modify Quotas แล้วระบบจะแสดงเว็บเพจดังภาพ ๑-128 และกดปุ่ม Network แล้วหลังจากนั้น ผู้ใช้จะเปลี่ยนค่าในช่อง Ports ให้เป็น 200 และกดปุ่ม Save เพื่อบันทึก quota ใหม่

ในภาพ ๑-129 เมื่อผู้ใช้ล็อกอินเข้าสู่ OpenStack Dashboard แล้วจะเห็นเว็บเพจ Overview ว่ามี quota network port เพิ่มขึ้น

๑.2.21 การรันวีเอ็มจากเกสต์โอเอสอิมเมจใน Volume เก่า

ในอันดับถัดไป สมมุติว่าผู้ใช้ไม่ต้องการใช้งานวีเอ็ม focal-vol แล้ว และตัดสินใจลบวีเอ็มออกจากระบบ แต่เนื่องจากหน่วยเก็บข้อมูลที่เราใช้เก็บอิมเมจของเกสต์โอเอสเป็นหน่วยเก็บข้อมูล Volume ที่จะไม่ถูกลบเมื่อมีการลบวีเอ็ม

ในภาพ ๑-130 ผู้ใช้ลบวีเอ็ม (Delete Instance) focal-vol ออกจาก Project หลังจากนั้น ผู้ใช้สามารถเรียกดูรายการหน่วยเก็บข้อมูล Volume ได้โดยเลือกแท็บ Volumes และแท็บย่อย Volumes ระบบจะแสดงรายการ Volume ดังภาพ ๑-131 ซึ่งจะมีสอง Volume และมีสถานะ Available ขอให้สังเกตว่า Volume ขนาด 10 GB เป็น Volume ที่เก็บข้อมูลดิสอิมเมจของเกสต์โอเอส

สมมุติว่า ผู้ใช้ต้องการสร้างวีเอ็มใหม่และใช้ Volume ขนาด 10 GB ดังกล่าวเป็นเกสต์โอเอสอิมเมจอีกครั้งหนึ่ง ผู้ใช้ก็สามารถทำได้โดยเลือกแท็บ Compute และแท็บย่อย Instance แล้วกดปุ่ม Launch Instance อย่างที่เคยปฏิบัติในตอนที่ 7.2.1.14 ระบบจะแสดงเว็บเพจเพื่อให้ใส่รายละเอียดของวีเอ็มซึ่งผู้ใช้จะตั้งชื่อวีเอ็มใหม่นี้ว่า reuse-focal ดังภาพ ๑-132 หลังจากกด Next ในหน้า Source ในภาพ ๑-133 ในช่อง Select Boot Source ผู้ใช้จะเลือก Volume (แทนที่จะเป็น image ซึ่งเป็นค่าดีฟอลต์) หลังจากนั้น เว็บเพจของหน้า Source จะเปลี่ยนไปเป็นเว็บเพจดังภาพ ๑-134 ในเว็บเพจเดียวกันผู้ใช้จะต้องเลือกว่าจะใช้หน่วยเก็บข้อมูล Volume ใดเป็นอิมเมจของเกสต์โอเอส ซึ่งโอเพนสแตคจะแสดงรายการให้เลือกใต้หัวข้อ Available ซึ่งผู้ใช้จะเลือก Volume ขนาด 10 GB และระบบจะแสดงเว็บเพจในภาพ ๑-135

ผู้ใช้จะกำหนดค่าอื่นๆเหมือนในตอน 7.2.1.14 ยกเว้นเมื่อถึงขั้นตอนในภาพ ๑-136 ที่ผู้ใช้จะเลือกให้นิคที่หนึ่งของวีเอ็มเชื่อมต่อกับระบบเครือข่ายเสมือน A-net-1 และนิคที่สองเชื่อมต่อกับ internal1 และหลังจากนั้นผู้ใช้จะทำเหมือนตอน 7.2.1.14 จนกระทั่งกดปุ่ม Launch Instance และระบบจะแสดงเว็บเพจดังภาพ ๑-137 ซึ่งจะปรากฏรายการข้อมูลของวีเอ็ม reuse-focal ขึ้น

ขอให้สังเกตว่า Component นิวตรอนของโอเพนสแตคจะกำหนดค่าไอพีใหม่ให้กับวีเอ็ม reuse-focal ในทุกการเชื่อมต่อกับระบบเครือข่ายเสมือน ในภาพ ๑-137 ค่าไอพีที่กำหนดให้ reuse-focal จะต่างจากที่เคยกำหนดค่าให้ focal-vol ในอดีต ในภาพ ๑-138 ผู้ใช้จะกำหนดให้ Fixed IP 10.50.11.250 ของนิคที่หนึ่งของวีเอ็มมีความเกี่ยวข้อง (associate) กับ Floating IP 192.168.20.176

ก่อนที่ผู้ใช้จะล็อกอินทางไกลไปยังวีเอ็มโดยใช้ Floating IP ดังกล่าว ผู้ใช้จะต้องลบข้อมูลตัวตนเก่าของคอมพิวเตอร์ที่ใช้ค่าไอพี 192.168.20.176 เดิม (เครื่อง focal-vol) ออกจากบันทึกของ Local คอมพิวเตอร์ก่อน ดังภาพที่ ๑-139 แล้วผู้ใช้จึงจะสามารถล็อกอินทางไกลเข้าใช้งานวีเอ็ม reuse-focal ด้วยไอพี 192.168.20.176 ได้ดังภาพ ๑-140

๑.3 การใช้งานด้วย Command Line Interfaces

คำสั่งแบบ Command Line Interfaces คือคำสั่งที่ผู้ใช้สามารถสั่งงานให้โอเพนสแตคปฏิบัติงานในฟังก์ชันต่างๆได้จาก Command Line ของ Local คอมพิวเตอร์ของผู้ใช้หรือจากวีเอ็ม โดยที่ Local คอมพิวเตอร์หรือวีเอ็มนั้นต้องสามารถติดต่อสื่อสารกับเครื่องคอนโทรลเลอร์โฮสต์และเอนด์พอยต์ของ OpenStack Service บนเครื่องคอนโทรลเลอร์ได้ (ผู้ใช้อาจใช้วีเอ็มของเครื่องโอเพนสแตคเพื่อออกคำสั่ง Command Line ของโอเพนสแตคก็ได้) ในคำบรรยายต่อไปนี้เราจะเรียก Local คอมพิวเตอร์หรือวีเอ็มดังกล่าวว่า Client คอมพิวเตอร์ (Client computer)

ผู้ใช้สามารถใช้คำสั่ง Command Line ในสถานการณ์ต่อไปนี้

  1. ผู้ติดตั้งระบบโอเพนสแตคใช้คำสั่ง Command Line ในระหว่างติดตั้ง ยกตัวอย่างเช่นการสร้างเซอร์วิส Project สำหรับ OpenStack Service และการสร้างเอ็นด์พ้อยของ Component เหล่านั้น

  2. ผู้ดูแลระบบมักจะใช้คำสั่ง Command Line สร้างสคริปต์สำหรับการสั่งงานเป็นชุด (batch) หรืองานที่ซับซ้อน

  3. แอปพลิเคชันสามารถเรียกใช้คำสั่ง Command Line เมื่อมีความจำเป็นต้องใช้งานฟังก์ชันของโอเพนสแตคเพื่อสนับสนุนการประมวลผลของแอปพลิเคชัน เช่นเพิ่มวีเอ็ม หรือ Volume โดยอัตโนมัติ เป็นต้น

ในอันดับถัดไป จะบรรยายการใช้ Command Line Interfaces ในสถานการณ์ต่อไปนี้

๑.3.1 การสร้าง Client คอมพิวเตอร์และเตรียมพร้อมสำหรับรันคำสั่ง Command Line

ในอันดับแรก สมมุติว่าผู้ใช้ระบบโอเพนสแตคหรือผู้ดูแลระบบต้องการออกคำสั่งระบบโอเพนสแตคด้วย Command Line เครื่อง Client คอมพิวเตอร์ของผู้ใช้ต้องสามารถเข้าถึงเว็บไซต์ http://<virtual IP address>/horizon และสามารถ login เข้าถึงหน้า API Access ใน Project ของผู้ใช้ในโอเพนสแตคได้

ในตัวอย่างต่อไปนี้ เราสมมุติว่าผู้ใช้สร้างวีเอ็มเครื่องหนึ่งในโอเพนสแตคชื่อ client1 ในภาพ ๑-141 ซึ่งจะใช้เป็นเครื่อง Ubuntu Linux สำหรับติดตั้งซอฟต์แวร์ Command Line Interface ของโอเพนสแตคเพื่อใช้ออกคำสั่ง Command Line ในบทนี้ สมมุติว่าเครื่อง client1 มี Floating IP address คือ 192.168.20.165 ผู้ใช้จะล็อกอินทางไกลจาก Local คอมพิวเตอร์ (เช่นโน๊ตบุ๊คของผู้ใช้) โดยใช้ซอฟต์แวร์ ssh และใช้คีย์​ KasiditOPS.pem

ก่อนที่จะสร้างวีเอ็มและรันวีเอ็ม ผู้ใช้จะสร้างไฟล์สำหรับให้คำสั่งสร้างวีเอ็มใช้คือไฟล์ config.file ซึ่งมีรหัสพาสเวิร์ดที่ผู้ใช้จะใช้เมื่อล็อกอินเข้าสู่วีเอ็ม ในอันดับถัดไปผู้ใช้จะรันวีเอ็มสองวีเอ็ม (ผู้ใช้สามารถกำหนดค่าแบบอื่นดูดูจากเว็บไซต์ cloud-init documentation ได้)

  2. --image ubuntu-focal-server : เกสต์โอเอสคือ Ubuntu 20.04 Server และใช้ Local storage บนเครื่อง compute host ที่รันวีเอ็มเก็บอิมเมจ เมื่อลบวีเอ็มอิมเมจนี้จะถูกลบไปด้วย

  3. โดยที่วีเอ็มทั้งสอง ต้องสามารถสื่อสารกันได้ และ

  4. สามารถสื่อสารกับอินเทอร์เน็ตได้ และ

  5. จะต้องอนุญาตให้คอมพิวเตอร์ภายนอกระบบโอเพนสแตคเรียกดูเว็บไซต์ บนวีเอ็มทั้งสองได้

ข้อ. 3 จงติดตั้งระบบฐานข้อมูลบนเครื่องวีเอ็มสามเครื่อง และใช้ระบบกาเลอร์ล่า (Galera) จัดการความซ้ำซ้อนของระบบฐานข้อมูลนั้น

ข้อ. 4 จงอธิบายข้อดีและข้อเสียของระบบจัดการเครือข่ายเสมือนแบบซ้ำซ้อน (VRRP) และระบบจัดการเครือข่ายเสมือนแบบกระจาย (DVR) ของระบบโอเพนสแตค
